# solid-kit: зонтичный дизайн-спек

- Дата: 2026-10-28
- Статус: черновик на ревью владельца. Решения, помеченные «владелец», приняты по ходу обсуждения; независимое ревью (Astra) проведено дважды: по первой версии (14 замечаний, закрыты) и по версии с контрактом фокуса, палитрой и корпусом грида (2026-10-29, вердикт «доработать», 15 замечаний; разбор в разделе 14). Каждый этап получает отдельный спек и план перед началом работ
- Объём документа: архитектура, распространение, токены, размеры, виртуализация, конвенции, инвентарь, дорожная карта. Подробные API компонентов сюда не входят.

## 1. Цель и не-цели

**Цель.** Личный UI-кит на Solid.js, который подключается в любой Solid-проект владельца одной строкой в `package.json` и попадает в бандл только теми компонентами, которые реально импортированы. Кит закрывает типовые задачи бэк-офисных интерфейсов: контролы форм, оверлеи, списки и, главное, универсальный грид с виртуализацией, группировкой и закреплёнными колонками.

**Не-цели первой итерации:**

- публикация в npm и любая сборка кита (`dist`, бандлинг, генерация `.d.ts`);
- поддержка Solid 2.0 (beta): целимся в `solid-js` 1.9;
- SSR и гидрация: кит рассчитан на клиентские SPA на Vite (решение владельца: проекты это бэк-офисы, SEO не нужен; SolidStart не используется);
- headless-библиотеки (Kobalte, Ark UI и подобные) и `solid-floating-ui`: всё поведение пишется самостоятельно;
- углублённая доступность: полные ARIA-паттерны WAI-ARIA, roving tabindex, ловушки фокуса, тестирование скринридерами. Закладываются семантичный HTML и разумный минимум (раздел 11). Обязательный минимум **блокирует приёмку** соответствующих компонентов: контраст текста 4.5:1, контраст индикатора фокуса и границ флажка и радио 3:1 (раздел 4.1), видимый и не перекрытый фокус (раздел 5.1), доступные имена у иконочных кнопок и прогресса, заявленная клавиатурная навигация;
- data-fetching внутри кита (TanStack Query и т. п.);
- горизонтальная виртуализация колонок грида, клиентская группировка строк внутри грида, экспорт;
- выбор «всего серверного результата» в гриде (выбор работает только по ключам загруженных строк, раздел 7);
- Storybook (может появиться позже поверх `playground/`, раздел 12).

## 2. Принятые решения

| Решение | Причина |
|---|---|
| Git-зависимость `github:StarkElessar/solid-kit#vX.Y.Z`, без npm | Так же распространяются конфиги владельца (`@stark/eslint-config`, `@stark/stylelint-config`); публикация не нужна |
| Исходники `.tsx/.ts/.css` без сборки кита | У потребителей есть Vite 8 и `vite-plugin-solid`, который трансформирует `.tsx` и из `node_modules` |
| Подпуть на компонент `@stark/solid-kit/<имя>` | Модульность и tree-shaking силами сборщика потребителя |
| Условие `"solid"` в `exports` | Без него `vite-plugin-solid` не исключит кит из `optimizeDeps` (раздел 3.3) |
| `solid-js` только в `peerDependencies` | Две копии `solid-js` ломают реактивность и контексты |
| CSS Modules на чистом CSS + CSS-переменные `--s-kit-*` | Потребителю не нужен `sass`; переменные и есть API кастомизации |
| `"sideEffects": ["**/*.css"]` | `false` целиком разрешает сборщику выбросить импорты CSS (раздел 3.4); гарантия для Vite 8/Rolldown подтверждается сборкой на этапе 0 |
| Явная высота контролов через `--s-kit-control-height` | Гарантированно одинаковая высота всех контролов (раздел 5) |
| Виртуализация всех списков по умолчанию, отключение только явным `virtualized={false}` | Списки и гриды владельца большие; производительность не должна зависеть от того, вспомнил ли автор страницы включить её (раздел 6) |
| `@floating-ui/dom` напрямую + собственный хук | Нужны только `computePosition` и middleware; поведение поповеров своё |
| `@tanstack/solid-virtual` | Проверенное ядро виртуализации, то же семейство, что `@tanstack/react-virtual` в референсе |
| Грид «глупый» и controlled, без data-fetching | Загрузка, кэш и пагинация остаются странице; кит не навязывает транспорт |
| Группировка в гриде только серверная: страница отдаёт готовые группы, грид рисует их и управляет UI группировки (`grouping`, свёрнутые группы) | Решение владельца: при серверной пагинации клиентская группировка загруженной страницы дала бы неполные группы и ложные суммы (раздел 7) |
| Выбор строк по ключам, сохраняется между страницами; главный чекбокс управляет только загруженными строками текущей страницы; «выбрать весь серверный результат» не поддерживается | Решение владельца: массовые операции опираются на данные, а не на DOM (раздел 7) |
| Vitest + `@solidjs/testing-library`, `playground/` вместо Storybook | Минимум инфраструктуры на старте |
| Префикс токенов и атрибутов `--s-kit-` / `data-s-kit-` | Решение владельца: короткий двухбуквенный префикс пересекается с другими библиотеками |
| Все производные цвета (hover, active, подсветка, фокус, выбранная строка, второй фон, тени) считаются через `color-mix(in oklch, …)` из нескольких базовых токенов | Смена одного `--s-kit-color-primary` перекрашивает всю систему (раздел 4.1) |
| Тема через `color-scheme: light dark` и `light-dark()` в базовых токенах; по умолчанию тема системная, `data-s-kit-theme` только задаёт `color-scheme` | Тёмная тема без дублирования токенов; нативные контролы и скроллбары перекрашиваются браузером (раздел 4.2) |
| Минимальные браузеры: Chrome/Edge 123, Firefox 125, Safari и iOS Safari 17.5 | Chrome/Edge и Safari определяются `light-dark()`, Firefox — Popover API (раздел 8); `color-mix()`, `oklch()` и CSS nesting поддержаны раньше (данные `@mdn/browser-compat-data`, приложение). Проекты владельца современные |
| Плавающие панели монтируются в хост рядом с инициатором (`PanelHost`, у грида — его корень) и поднимаются в top layer через `popover="manual"` + `showPopover()`, а не переносятся в `body`. **Подтверждено владельцем** | Панель наследует все токены, тему и размер обёртки и обновляется при их смене, не обрезается `overflow` предков, работает поверх модального `<dialog>` (раздел 8). Цена: минимальный Firefox 125; нужны изоляция событий и сброс наследуемых свойств на корне панели (разделы 8.1–8.3). Запасной вариант, если приёмка этапа 0 или 2 провалится: портал в `body` с копированием токенов якоря. Он ранее отвергнут как недостаточный (теряет произвольные токены и не следит за их сменой), но допустим как отступление с явной фиксацией ограничений |
| Relative color syntax (`oklch(from …)`) и `contrast-color()` не используются | Поднимают минимальные версии: данные о relative color в Safari расходятся (MDN: 18, caniuse: полная поддержка только с 27), `contrast-color()` есть только в Chrome 147, Firefox 146, Safari 26 |
| Виртуализация без порога: никакого условного включения по числу элементов и никакой внутренней оптимизации для малых списков | Решение владельца: один путь рендера, обещание «виртуализация всегда» выполняется буквально (раздел 6) |
| Высоты контролов 28 / 32 / 40 px | Утверждено владельцем; правятся в одном месте (раздел 5) |
| Имя пакета `@stark/solid-kit` | Утверждено владельцем; по аналогии с `@stark/eslint-config` и `@stark/stylelint-config` |
| Репозиторий публичный; секреты в него не коммитятся | Решение владельца: git-зависимость ставится без ключей и токенов, правила публичных репозиториев действуют с первого коммита (раздел 11) |
| Направление дизайна в духе Apple: плоские заливки без градиентов, тонкие границы, мягкие радиусы, сегментированный контрол для ToggleGroup в режиме single, tinted-кнопки, спокойные нейтральные цвета, полупрозрачный материал панелей с запасным сплошным фоном (раздел 4.3). Палитра **Мята** (выбор владельца, 2026-10-29; 2026-10-28 по прототипу была выбрана Синяя, она осталась примером в playground вместе с Моно; Изумруд, Фиолет и Роза отклонены), шрифт интерфейса IBM Plex Sans | Решение владельца по прототипу. Базовые токены Мяты (светлая / тёмная): primary `#17785a` / `#4fc79c`, contrast `#fff` / `#04162e`, surface `#fff` / `#1c1c1e`, text `#1d1d1f` / `#f5f5f7`, border `#d2d2d7` / `#3a3a3c`, danger `#d70015` / `#ff6961`, success `#437a12` / `#8fd14f`, warning `#a85200` / `#ffb340`, радиус 8 px; контраст пар проверяет этап 0. Смена палитры это смена базовых токенов (раздел 4.1). `success` сдвинут к жёлто-зелёному (оттенок около 92°, у Мяты около 160°), чтобы не сливаться с primary; контраст на поверхности 5,21:1 и 9,24:1. Кит не поставляет файлы шрифтов: `--s-kit-font` по умолчанию `'IBM Plex Sans', system-ui, sans-serif`, шрифт подключает потребитель (раздел 3.5) |
| Индикатор фокуса — `:focus-visible` с `outline` двух вариантов (внешний и внутренний), выбор по близости обрезающего предка | Фокус не должен обрезаться `overflow` контейнеров и закрываться липкими областями (раздел 5.1) |
| Даты и время (этап 5): свои хелперы поверх `Date` в UTC + `Intl` для форматирования и локали, без библиотек дат и полифилов | Решение владельца; причина отказа от нативного API дат в приложении |

| Паттерны: compound components, render props, принципы SOLID, отдельные паттерны GoF по месту | Требование владельца; правила применения в разделе 11.1 |

## 3. Распространение и форма пакета

### 3.1. Раскладка репозитория

```
solid-kit/
├─ package.json            # пакет в корне: pnpm add github:... ставит корень
├─ pnpm-workspace.yaml     # packages: [playground]; нужен только для локальной линковки кита в playground
├─ tsconfig.json           # строгий (раздел 3.6)
├─ src/
│  ├─ styles/tokens.css    # глобальные --s-kit-* переменные, атрибуты размера и темы
│  ├─ utils/               # createControllableSignal, позиционирование, слои, общие хелперы
│  └─ components/
│     ├─ button/           # index.ts, button.tsx, button.module.css
│     ├─ popover/          # index.ts, popover.tsx, popover.module.css
│     ├─ context-menu/  ├─ select/  ├─ grid/  ...
└─ playground/             # отдельное Vite-приложение, зависит от "@stark/solid-kit": "workspace:*"
```

`playground/` не входит в `exports` и в `files`, потребителю он недоступен. Внутренние примитивы (`ListBox`) лежат в `src/components/list-box/`, но в README публичными не объявляются: подпуть технически доступен через wildcard, стабильность его API не гарантируется.

### 3.2. `package.json`

```json
{
  "name": "@stark/solid-kit",
  "version": "0.1.0",
  "type": "module",
  "files": ["src"],
  "sideEffects": ["**/*.css"],
  "exports": {
    "./tokens.css": "./src/styles/tokens.css",
    "./package.json": "./package.json",
    "./*": {
      "solid": "./src/components/*/index.ts",
      "default": "./src/components/*/index.ts"
    }
  },
  "peerDependencies": { "solid-js": "^1.9.0" },
  "dependencies": {
    "@floating-ui/dom": "^1.8.0",
    "@tanstack/solid-virtual": "^3.13.50"
  }
}
```

В `devDependencies`: `solid-js@1.9.17`, `vite@8.3.5`, `vite-plugin-solid@2.11.14`, `typescript`, `vitest`, `@solidjs/testing-library`, `@stark/eslint-config` и `@stark/stylelint-config` (git-зависимости). Скриптов `prepare`/`postinstall` нет, кит сам ничего не собирает. Это не описывает весь процесс подготовки git-пакета pnpm (как он упаковывает репозиторий, применяет `files`, ставит ли devDependencies): это проверяется матрицей этапа 0 (раздел 12, критерий 1).

Подключение у потребителя:

```jsonc
// package.json потребителя
"dependencies": { "@stark/solid-kit": "github:StarkElessar/solid-kit#v0.3.0" }
```

```ts
// точка входа приложения, один раз
import '@stark/solid-kit/tokens.css';
// в любом модуле
import { Select } from '@stark/solid-kit/select';
```

### 3.3. `exports`, wildcard и условие `solid`

- `"./*"` подставляет совпавшую часть во все `*` справа: `@stark/solid-kit/select` → `./src/components/select/index.ts`. Точные ключи (`./tokens.css`, `./package.json`) имеют приоритет над шаблоном, поэтому `tokens.css` не уходит в `src/components/tokens.css/index.ts`. Корневой импорт `@stark/solid-kit` намеренно не экспортируется (ошибка `ERR_PACKAGE_PATH_NOT_EXPORTED`): так нельзя случайно затянуть весь кит одним импортом.
- Условие `"solid"` нужно не для резолва, а как маркер: `vite-plugin-solid` через `vitefu.crawlFrameworkPkgs` ищет ключ `solid` рекурсивно **только в поле `exports`** (`containsSolidField(pkgJson.exports)`), и найденный пакет исключается из `optimizeDeps` и добавляется в SSR `noExternal`. Плагин также добавляет `solid` в начало `resolve.conditions`.
- `"default"` указывает на те же исходники, чтобы `tsc` потребителя (`moduleResolution: "bundler"`, без `customConditions`) находил типы прямо в `.ts`/`.tsx`; отдельного `"types"` не нужно.
- Зависимости кита (`@floating-ui/dom`, `@tanstack/solid-virtual`) vitefu обходит как зависимости framework-пакета; в глубокий `optimizeDeps.include` он добавляет только пакеты без `module`/`exports` (эвристика CJS), а у обеих зависимостей есть `exports`. Что `solid-js` при этом остаётся в одной копии и в dev, и в build, не проверено чтением исходников и подтверждается критерием приёмки 1 (раздел 12).

### 3.4. `sideEffects`

Каждый компонент импортирует свой `.module.css`, а точка входа потребителя импортирует `tokens.css` только ради побочного эффекта. Если объявить `"sideEffects": false` целиком, сборщик вправе считать любой модуль пакета чистым и выбросить импорт, чей результат не используется: первым пострадает `import '@stark/solid-kit/tokens.css'`, а у сборщиков, которые не размечают CSS сами, и стили компонентов. Поэтому JS/TS объявляется чистым (tree-shaking неиспользуемых экспортов работает), а CSS явно помечается как имеющий побочные эффекты: `"sideEffects": ["**/*.css"]`.

Уточнение по Vite 8.3.5 (прочитано в исходнике): плагин `vite:css-post` сам возвращает `moduleSideEffects: "no-treeshake"` для обычного CSS и `false` для CSS Modules (их стили остаются, пока используется объект классов). То есть в Vite риск ниже, но правило обязательно: оно верно описывает пакет и не зависит от внутренностей конкретной версии Vite. Гарантия кита распространяется на Vite 8 (Rolldown) и подтверждается сборкой в критерии этапа 0; другие сборщики не проверяются.

### 3.5. Что требуется от проекта-потребителя

- Vite 8 и `vite-plugin-solid` 2.11+ (для Vite 8 плагин сам задаёт `rolldownOptions.transform.jsx: 'preserve'`);
- `solid-js` ^1.9 в собственных зависимостях;
- подключённый шрифт IBM Plex Sans с кириллицей (лицензия OFL; Google Fonts или локальные файлы): кит только ссылается на него в `--s-kit-font` и без него падает на `system-ui`;
- типы `vite/client` в tsconfig (в них объявлены `*.module.css` и `*.css`), `jsx: "preserve"`, `jsxImportSource: "solid-js"`, `moduleResolution: "bundler"`;
- однократный импорт `@stark/solid-kit/tokens.css`.

Настройки `optimizeDeps`, `ssr.noExternal` и `resolve.dedupe` не требуются: матрица этапа 0 прошла без них (источник `git+file://`; повтор с `github:` после публикации).

### 3.6. Типы и строгость

`tsc` потребителя проверяет исходники кита как обычный код (`skipLibCheck` пропускает только `.d.ts`). Проверено на `typescript` 5.9.3 и 7.0.2: ошибка внутри `node_modules/@stark/solid-kit/src/...` при `skipLibCheck: true` выводится. Поэтому кит обещает компиляцию не «при любых настройках», а в **поддерживаемой матрице потребителя**:

| Параметр | Поддерживается |
|---|---|
| TypeScript | 5.9 и 7.x (резолв и проверка исходников проверены на 5.9.3 и 7.0.2) |
| `target` | `ES2022` и новее (рекомендация, не проверялась прогоном) |
| `lib` | `ES2023`, `DOM`, `DOM.Iterable` (рекомендация: кит может использовать `Array.prototype.at`, `toSorted`) |
| JSX | `jsx: "preserve"`, `jsxImportSource: "solid-js"` |
| Модули | `module: "ESNext"` или `"Preserve"`, `moduleResolution: "bundler"` |
| Типы | `vite/client` |

Синтаксис исходников кита: стандарт ECMAScript, поддержанный минимальными браузерами (раздел 2), без `enum`, `namespace`, декораторов и параметров-свойств. Внутри матрицы кит держится под самым строгим набором флагов, чтобы строгость потребителя не находила в нём ошибок: `strict`, `exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`, `noImplicitOverride`, `noImplicitReturns`, `noFallthroughCasesInSwitch`, `noPropertyAccessFromIndexSignature`, `noUnusedLocals`, `noUnusedParameters`, `verbatimModuleSyntax`, `isolatedModules`, `erasableSyntaxOnly` (никаких `enum` и `namespace`). Сам кит разрабатывается на TypeScript 5.9.3 (peer `@stark/eslint-config` ограничен `<6.1`); потребительская матрица на 5.9.3 и 7.0.2 прогоняется скриптом `scripts/verify-package-form.sh`.

### 3.7. Версии и теги

- Версия в `package.json` и аннотированный git-тег `vX.Y.Z` меняются одним коммитом; описание изменений пишется в сообщении тега.
- До завершения этапа 4б (тег `v1.0.0`) действует `0.x`: несовместимое изменение поднимает minor, остальное поднимает patch.
- Потребитель указывает тег; lockfile pnpm фиксирует конкретный коммит, поэтому сборки воспроизводимы, а обновление делается сменой тега.

## 4. Система стилей и токенов

- Стили только на чистом CSS: `*.module.css` на компонент плюс глобальный `tokens.css`. Нативный nesting допустим. SCSS, PostCSS-плагины и CSS-in-JS не используются.
- Хэшированные классы CSS Modules снаружи не перебить, поэтому **публичный API кастомизации это CSS-переменные**. Дополнительно каждый компонент принимает `class` и `style` и навешивает их на корневой элемент.
- Префикс токенов `--s-kit-`, префикс атрибутов `data-s-kit-`. Корневой элемент каждого компонента кита и каждой плавающей панели несут атрибут `data-s-kit` (он нужен для пересчёта производных токенов, раздел 4.1).
- Три слоя токенов:
  - **базовые** (публичные, задаёт пользователь): несколько цветов, радиусы, шрифты, высоты контролов, z-index слоёв. Объявлены в `tokens.css` на `:root`, переопределяются на `:root` или на любой обёртке;
  - **производные** (внутренние): все состояния и оттенки, вычисленные из базовых через `color-mix()`. Объявлены в `tokens.css` на `:root, [data-s-kit]`. Переопределять их на обёртке нельзя (корень компонента пересчитает их заново); для точечной настройки служат базовые или компонентные токены;
  - **компонентные** (публичные: `--s-kit-select-bg`, `--s-kit-grid-row-selected-bg`, ...) **нигде не объявляются**, компонент читает их с фолбэком на производный или базовый токен.

Почему компонентные токены читаются с фолбэком, а не объявляются: кастомное свойство без `@property` хранит значение как последовательность токенов, `var()` в нём подставляется там, где свойство объявлено, а дальше наследуется готовый результат. Объявленный на самом элементе `--s-kit-select-bg` не дал бы переопределить его с предка, а объявленный на `:root` `--s-kit-select-bg: var(--s-kit-color-surface)` не увидел бы `--s-kit-color-surface`, переопределённый на обёртке. По той же причине производные токены пересчитываются не только на `:root`, но и на корне каждого компонента (`[data-s-kit]`): иначе `--s-kit-color-primary-hover`, вычисленный на `:root`, не заметил бы `--s-kit-color-primary`, переопределённый на обёртке. Переключение темы этой ловушки не имеет: `light-dark()` внутри кастомного свойства не вычисляется при подстановке, а остаётся функцией до момента использования в реальном цветовом свойстве и разрешается по `color-scheme` того элемента, где применяется (раздел 4.2).

```css
/* select.module.css (фрагмент) */
.control {
  background: var(--s-kit-select-bg, var(--s-kit-color-surface));
  border-color: var(--s-kit-select-border, var(--s-kit-color-border));
  border-radius: var(--s-kit-select-radius, var(--s-kit-radius));
}
```

- Каждый `.module.css` начинается с комментария со списком своих компонентных токенов; страница компонента в playground показывает пример их переопределения.
- В стилях компонентов нет литералов цветов, радиусов и размеров шрифта: только токены (правило линтера в разделе 11).

### 4.1. Цвета: всё производное из нескольких базовых токенов

Принцип: компонент читает только производный (или компонентный) токен, производный токен вычисляется из базового, в компонентном CSS нет ни одного литерала цвета. Базовых цветов минимум (YAGNI): `--s-kit-color-primary`, `--s-kit-color-primary-contrast`, `--s-kit-color-surface`, `--s-kit-color-text`, `--s-kit-color-border`, `--s-kit-color-danger`, `--s-kit-color-success`, `--s-kit-color-warning`.

`--s-kit-color-primary-contrast` (текст на primary) остаётся базовым, хотя его хотелось бы вычислять: автоматический контраст требует `contrast-color()` или relative color syntax, а они поднимают минимальные версии браузеров (раздел 2).

```css
/* tokens.css (фрагмент; полный файл: src/styles/tokens.css) */
:root {
  color-scheme: light dark;
  --s-kit-color-primary: light-dark(#17785a, #4fc79c);
  --s-kit-color-primary-contrast: light-dark(#fff, #04162e);
  --s-kit-color-surface: light-dark(#fff, #1c1c1e);
  --s-kit-color-text: light-dark(#1d1d1f, #f5f5f7);
  --s-kit-color-border: light-dark(#d2d2d7, #3a3a3c);
  --s-kit-color-danger: light-dark(#d70015, #ff6961);
  --s-kit-color-success: light-dark(#437a12, #8fd14f);
  --s-kit-color-warning: light-dark(#a85200, #ffb340);
  --s-kit-radius: 8px;
  --s-kit-font: 'IBM Plex Sans', system-ui, sans-serif;
  /* размеры контролов, фокус (раздел 5.1), материал панели (раздел 4.3), z-index */
}

:root,
[data-s-kit] {
  --s-kit-color-primary-hover: color-mix(in oklch, var(--s-kit-color-primary), var(--s-kit-color-text) 14%);
  --s-kit-color-primary-active: color-mix(in oklch, var(--s-kit-color-primary), var(--s-kit-color-text) 26%);
  --s-kit-color-primary-subtle: color-mix(in oklch, var(--s-kit-color-primary) 10%, var(--s-kit-color-surface));
  --s-kit-color-focus-ring: color-mix(in oklch, var(--s-kit-color-primary) 75%, transparent);
  --s-kit-color-muted: color-mix(in oklch, var(--s-kit-color-text) 62%, var(--s-kit-color-surface));
  --s-kit-color-hover: color-mix(in oklch, var(--s-kit-color-text) 5%, var(--s-kit-color-surface));
  --s-kit-color-tint: color-mix(in oklch, var(--s-kit-color-text) 7%, var(--s-kit-color-surface));   /* -hover 11 %, -active 16 % */
  --s-kit-color-row-selected: color-mix(in oklch, var(--s-kit-color-primary) 9%, var(--s-kit-color-surface));
  --s-kit-color-surface-2: color-mix(in oklch, var(--s-kit-color-text) 4%, var(--s-kit-color-surface));
  --s-kit-color-group: color-mix(in oklch, var(--s-kit-color-text) 2%, transparent);
  /* линии полупрозрачные и считаются от text: мягкие на любом фоне (решение владельца по прототипу) */
  --s-kit-color-hairline: color-mix(in oklch, var(--s-kit-color-text) 8%, transparent);
  --s-kit-color-border-strong: color-mix(in oklch, var(--s-kit-color-text) 14%, transparent);
  --s-kit-color-control-edge: color-mix(in oklch, var(--s-kit-color-text) 50%, transparent);
  --s-kit-color-panel: color-mix(in oklch, var(--s-kit-color-surface) var(--s-kit-panel-opacity), transparent);
  --s-kit-shadow-color: color-mix(in oklch, var(--s-kit-color-text) 18%, transparent);
  --s-kit-shadow-popover: 0 10px 30px var(--s-kit-shadow-color), 0 0 0 0.5px var(--s-kit-color-border-strong);
  /* -subtle и -hover для danger/success/warning по той же схеме */
}
```

- **Почему `oklch`.** Пространство перцептивно равномерное: одинаковый процент примеси даёт одинаковый видимый сдвиг светлоты для любого primary, без «грязных» середин, как при смешивании в sRGB. У ахроматических цветов (текст, поверхность, `transparent`) оттенок «пустой», и `color-mix` в `oklch` берёт оттенок второго цвета, поэтому примесь серого не сдвигает hue primary. Если когда-нибудь понадобится смешать два разных хроматических цвета, использовать `in oklab`: полярная интерполяция в `oklch` идёт по кругу оттенков и даёт неожиданные промежуточные цвета.
- **Почему hover и active смешиваются с `--s-kit-color-text` (решение владельца, 2026-10-29).** Первая формула смешивала с `--s-kit-color-primary-contrast`: так состояние заметно у любой палитры, но заливка двигается к цвету текста кнопки, и контраст текста падает. Измерено в Chrome на странице «Темы» для Синей палитры: светлая тема покой 4,70:1, hover 3,61:1, active 2,94:1; тёмная покой 6,90:1, hover 5,27:1, active 4,10:1 (порог 4,5:1). Смесь с `text` (14 % и 26 %) заливку от текста кнопки отодвигает: контраст растёт. Мята, светлая / тёмная: покой 5,43 / 8,61, hover 6,17 / 9,26, active 6,94 / 9,94 (при 10 % и 20 % у светлой Мяты сдвиг hover был 10, что меньше порога заметности 12). Цена: палитре, у которой primary почти равен `text` (Моно), смесь с `text` ничего не меняет, поэтому такая палитра переопределяет `--s-kit-color-primary-hover` и `--s-kit-color-primary-active` смесью с `primary-contrast` (так сделано в Моно на странице «Темы»: контраст 16,83 / 11,81 / 8,13 светлая, 15,46 / 11,21 / 8,35 тёмная). Покой, hover и active проверяются на странице «Темы» (раздел 12, критерий 5) для палитр Мята, Синий и Моно в обеих темах.
- **Линии и выделение (решения владельца по прототипу).** Линии тонкие и полупрозрачные (`--s-kit-color-hairline` 8 %, `--s-kit-color-border-strong` 14 %); жёсткие рамки не используются. Единственная заметная рамка у флажка и радио (`--s-kit-color-control-edge`, 50 % текста: контраст границы к поверхности не ниже 3:1, WCAG 1.4.11; при 42 % светлая тема давала 2,61:1; проверяет `tokens.test.ts`). Поля ввода и триггеры списков белые (`--s-kit-color-surface`) с границей `--s-kit-color-control-edge` (решение владельца 2026-10-29, вопрос 8: контраст границы к поверхности не ниже 3:1 в обеих темах, WCAG 1.4.11; `border-strong` остаётся у линий панелей и заголовков групп); ошибка поля это красная рамка, кольцо и текст ошибки, без красной заливки. Выбранное и активное (пункт списка и меню, вкладка, дата, строка) показывается лёгкой заливкой, а не рамкой или подчёркиванием; сплошной primary остаётся только у главной кнопки. У выбранной строки грида дополнительно акцентная полоска слева (`inset box-shadow` в первой ячейке, не обрезается `overflow`). Заголовок группы в списках: полупрозрачный фон `--s-kit-color-group` без скругления, нижнее подчёркивание `--s-kit-color-border-strong` и счётчик справа; залипает сверху (`position: sticky`) с `backdrop-filter: blur`, чтобы прокручиваемые под ним пункты не мешали читать. Сама группа без заливки. Отступы внутри панели 6 px со всех сторон, зазор между пунктами 2 px, переходы фона 150 мс (отключаются при `prefers-reduced-motion`).
- **Градиенты по умолчанию не используются** (решение владельца, направление Apple — плоские заливки). Шапка грида и кнопки — плоский фон (`--s-kit-color-surface-2` у шапки, `--s-kit-color-primary` у основной кнопки) и тонкая граница. Если градиент понадобится, это ещё один производный токен через `color-mix` от базовых, и требование «смена primary перестраивает всё» на него распространяется.
- `light-dark()` принимает только цвета, поэтому темозависимые тени собираются из цветовых токенов (`--s-kit-shadow-color`), а не задаются через `light-dark()` целиком.
- **Пример перекраски.** Обёртка `<section style="--s-kit-color-primary: light-dark(#7c3aed, #a78bfa)">` перекрашивает внутри себя заливку и hover кнопки, фокус-кольцо и подсветку опции Select, выбранную строку грида: каждый корень компонента (`[data-s-kit]`) пересчитывает производные токены из переопределённого primary. Выпадающие панели остаются в DOM внутри обёртки и наследуют её токены так же, как сам компонент (раздел 8).

### 4.2. Темы через `color-scheme` и `light-dark()`

- Базовые цветовые токены объявлены через `light-dark(светлый, тёмный)`, на `:root` стоит `color-scheme: light dark`: по умолчанию тема следует системной.
- Принудительная тема задаёт только `color-scheme`, сами токены не переопределяются:

```css
[data-s-kit-theme='light'] { color-scheme: light; }
[data-s-kit-theme='dark'] { color-scheme: dark; }
```

- Атрибут работает на `<html>` и на любой обёртке: `color-scheme` наследуется, а `light-dark()` разрешается по используемой `color-scheme` элемента, к которому применяется цвет. Производные токены, объявленные на `:root`, остаются корректными: после подстановки `var()` в них лежит `color-mix(…, light-dark(…), …)`, который вычисляется уже на элементе-потребителе.
- Цветовые токены **не регистрируются через `@property`** с `syntax: '<color>'`: у зарегистрированного свойства значение вычисляется в абсолютный цвет на элементе, где оно объявлено, и тема или primary, переопределённые ниже по дереву, перестают на него влиять.
- Бонус `color-scheme`: нативные `<input>`, `<select>`, `<dialog>` и полосы прокрутки браузер перекрашивает сам.
- Без браузера проверить можно только по спецификациям и данным совместимости. Поэтому поведение на практике (тема на обёртке, вложенный `light-dark()` внутри `color-mix()` в кастомном свойстве, переопределение primary на обёртке, плавающие панели в top layer) **проверяется в playground и входит в критерии приёмки этапа 0** (раздел 12, критерий 5).

### 4.3. Материал панелей

Фон плавающих панелей (Select, Combobox, MultiSelect, ContextMenu, Popover) может быть полупрозрачным с `backdrop-filter: blur(var(--s-kit-panel-blur))`, как материал в Apple-интерфейсах; `--s-kit-panel-blur` по умолчанию умеренный, а степень прозрачности — производный токен через `color-mix` от `--s-kit-color-surface`. Обязателен запасной сплошной фон `--s-kit-color-surface`: когда браузер не поддерживает ни `backdrop-filter`, ни `-webkit-backdrop-filter` (условие `@supports` пишется в положительной форме `(backdrop-filter: …) or (-webkit-backdrop-filter: …)`), и при `@media (prefers-reduced-transparency: reduce)`. По MDN `backdrop-filter` без префикса есть в Safari с 18, а в 17.5 — только `-webkit-backdrop-filter`, поэтому указываются оба свойства. `prefers-reduced-transparency` поддержан только в Chrome/Edge 118+, в Safari и Firefox его нет. Контраст текста 4.5:1 обязателен на любом фоне под панелью: прозрачность не должна ухудшать читаемость. Исполнимое правило: материал это `--s-kit-color-panel` (`surface` с непрозрачностью `--s-kit-panel-opacity` 82 %) и `backdrop-filter: blur(var(--s-kit-panel-blur))` (20 px); читаемость проверяется численно на самых неблагоприятных подложках (чёрной и белой), минимум 4.5:1 (страница «Темы»). Размытие однородного неподходящего фона контраст не улучшает, поэтому при провале проверки панель получает сплошной фон. Залипающий заголовок группы в списках получает под полупрозрачной заливкой `--s-kit-color-group` сплошной фон `--s-kit-color-surface`, иначе прокручиваемые под ним пункты просвечивают. Сами плотные слои данных (тело грида, таблицы, строки списков) материалом не делаются: он только у фона панелей. Если под панелью плотные данные и контраст 4.5:1 с прозрачностью не держится, панель получает сплошной фон. Источник ограничений — запись Liquid Glass в базе ui-ux-pro-max: «навигация и контролы, не плотные слои данных, с запасным вариантом для доступности».

## 5. Единая высота контролов

Требование: все кнопки, инпуты, селекты и прочие контролы строго одной высоты в пределах размера. Высота задаётся **явно**, а не выводится из `padding + line-height + border`.

- Токены `--s-kit-control-height-sm / -md / -lg`, по умолчанию 28 / 32 / 40 px, правятся в одном месте (`tokens.css`).
- Каждый контрол: `box-sizing: border-box; height: var(--s-kit-control-height, var(--s-kit-control-height-md));` рамка входит в высоту; содержимое выравнивается через `display: inline-flex; align-items: center`, так что `line-height` и шрифт на высоту не влияют.
- Вместе с высотой масштабируются `--s-kit-control-padding-x` и `--s-kit-control-font-size` (тот же механизм).
- Размер выбирается пропом `size="sm" | "md" | "lg"`. Компонент рендерит его как атрибут `data-s-kit-size` на корневом элементе, а `tokens.css` содержит глобальные правила:

```css
[data-s-kit-size='sm'] { --s-kit-control-height: var(--s-kit-control-height-sm); /* + padding, font-size */ }
[data-s-kit-size='md'] { --s-kit-control-height: var(--s-kit-control-height-md); }
[data-s-kit-size='lg'] { --s-kit-control-height: var(--s-kit-control-height-lg); }
```

- Тот же атрибут ставится на обёртку (форма, тулбар, грид), когда нужно «весь блок в sm»: потомки без пропа `size` наследуют переменную. Контрол без пропа `size` переменную не объявляет, иначе он перекрыл бы значение обёртки.
- **Единое правило разрешения размера.** Переменная `--s-kit-control-height` может быть не объявлена (нет ни пропа, ни обёртки), поэтому **каждое** геометрическое свойство, завязанное на размер, читает её только в форме `var(--s-kit-control-height, var(--s-kit-control-height-md))`: высота контролов, `width` и `height` IconButton, высота строки Checkbox/Radio/Switch, высота строки ListBox. Голое `var(--s-kit-control-height)` в компонентном CSS запрещено (проверяется на ревью). Числовая оценка для виртуализатора берётся по тому же правилу (раздел 6).
- IconButton квадратная: ширина равна высоте по правилу выше.
- ButtonGroup и ToggleGroup: контейнер с внутренним отступом 2 px и зазором 2 px между кнопками (`--s-kit-color-tint` под группой), у каждой кнопки собственное скругление; выбранная кнопка (multi) заливается лёгким `--s-kit-color-primary-subtle` и не занимает всю высоту и ширину группы. Высота группы равна высоте контрола, кнопки внутри на 4 px ниже. Единицей сравнения высоты в ряду контролов служит оболочка группы, а кольцо фокуса сегментов внутреннее (раздел 5.1).
- Checkbox, Radio, Switch: сама отметка меньше, но строка «отметка + label» (и без label) имеет ту же высоту, поэтому стоит в одной линии с инпутами.
- MultiSelect по умолчанию держит фиксированную высоту: выбранные значения показываются в одну строку, не поместившееся сворачивается в счётчик «+N»; третий режим `chipsOverflow="summary"` показывает один чип «2 из 43» со стрелкой, клик по нему открывает список (решение владельца). `N` — число выбранных значений, в том числе вне текущего результата поиска; `M` — проп `total`, а без него число элементов `items`; при `N > M` (внешний поиск без `total`) чип показывает только «N выбрано», при `N = 0` плейсхолдер, при всех выбранных «43 из 43»; рост контрола в высоту запрещён. Ограничение снимается пропом `chipsOverflow="wrap"` (по умолчанию `"collapse"`): чипы переносятся на следующие строки и контрол растёт. Решение владельца. MultiSelect с `chipsOverflow="wrap"` осознанно выпадает из правила единой высоты и в проверке ряда контролов не участвует (на странице «Контролы в ряд» показывается отдельной строкой с пометкой).
- Высота строки ListBox по умолчанию равна высоте контрола текущего размера.

**Критерий приёмки:** страница playground «Контролы в ряд» показывает на одной линии button, icon-button, button-group, toggle-group, input, numeric, select, combobox, multiselect (с чипами и счётчиком «+N»), datepicker, switch, checkbox и radio в светлой и тёмной теме в пяти рядах: (1) без `size` и без обёртки (фолбэк на `md`); (2) обёртка `data-s-kit-size="sm"`, у контролов `size` нет; (3) то же с `lg`; (4) обёртка `sm`, у части контролов локально `size="lg"` — они выше соседей, остальные остаются `sm`; (5) явный `size` у каждого контрола. Верх и низ контролов одного размера в ряду совпадают пиксель в пиксель (проверка глазами плюс встроенная в страницу проверка, которая сравнивает `getBoundingClientRect()` и выводит отклонения). Компоненты, которые ещё не реализованы, добавляются на страницу в своём этапе; datepicker появится на этапе 5. В каждом ряду каждый контрол фокусируется с клавиатуры: внешнее кольцо видно целиком и не сдвигает соседей (`outline` не участвует в раскладке); у сегментов ButtonGroup и ToggleGroup кольцо внутреннее и проверяется внутри оболочки группы.

### 5.1. Индикатор фокуса и контейнеры с `overflow`

- **Индикатор фокуса** — `:focus-visible` с `outline`, а не `box-shadow` и не цвет рамки. Токены: `--s-kit-focus-width` (2px), `--s-kit-focus-offset` (2px), цвет `--s-kit-color-focus-ring` (производный из primary, раздел 4.1), `--s-kit-focus-space` = width + offset. `outline: none` без замены запрещён. *Предложение* для линтера: правило stylelint кита, запрещающее `outline: none` и `outline: 0` в `src/components/**/*.module.css` (например, `declaration-property-value-disallowed-list`) с исключением для правил, где тут же задано кольцо из токенов. Уточняется на этапе 0.
- **Почему нужны два варианта.** И `outline`, и внешний `box-shadow` рисуются снаружи элемента и обрезаются любым предком с `overflow: hidden | auto | scroll | clip`, в том числе предком со скруглением, который клипует содержимое. Панели в top layer (раздел 8) не обрезаются. Обрезаются элементы внутри ячеек грида и обёртки таблицы, прокручиваемых списков, области чипов MultiSelect (`overflow: hidden`), вкладок с горизонтальной прокруткой, тела Dialog.
- **Внешнее кольцо** (по умолчанию): `outline: var(--s-kit-focus-width) solid var(--s-kit-color-focus-ring); outline-offset: var(--s-kit-focus-ring-offset, var(--s-kit-focus-offset))`.
- **Внутреннее кольцо:** то же кольцо с `outline-offset: calc(-1 * var(--s-kit-focus-width))`, то есть внутри рамки элемента. Включается глобальным правилом `tokens.css` для потомков контейнера с атрибутом `data-s-kit-focus-inset`: он задаёт `--s-kit-focus-ring-offset`, и все кольца внутри переходят на внутренний вариант. Кольцо цвета primary поверх заливки primary даёт 1:1 (кнопка с фоном primary внутри обрезающего контейнера), поэтому для компонентов с заливкой primary или danger этап 1 вводит отдельный цвет внутреннего кольца с контрастом к заливке (требование приёмки этапа 1). Кольцо на поверхности: `--s-kit-color-focus-ring` (75 % primary) даёт 3,15:1 в светлой и 4,21:1 в тёмной теме при пороге 3:1.
- **Правило выбора:** элемент, у которого ближайший обрезающий предок ближе к краю, чем `--s-kit-focus-space`, использует внутреннее кольцо.

  | Где | Вариант |
  |---|---|
  | Ячейки и строки грида, кнопки и чипы в полосах корпуса грида (раздел 10.1) | внутреннее |
  | Пункты ListBox, ContextMenu, меню колонок | внутреннее |
  | Чипы в MultiSelect, вкладки в прокручиваемом списке Tabs | внутреннее |
  | Кнопки в тулбарах внутри обрезающих контейнеров, сегменты ToggleGroup и ButtonGroup (кнопки внутри контейнера с отступом) | внутреннее |
  | Свободные контролы в форме и в теле Dialog с резервным отступом | внешнее |

- **Обрезающие контейнеры кита** (скроллер ListBox, тело Dialog, корпус грида, скроллер Tabs) делают одно из двух: резервируют внутренний отступ не меньше `--s-kit-focus-space` вокруг содержимого (тело Dialog, у которого свободные контролы) или ставят `data-s-kit-focus-inset` (корпус грида, ListBox, Tabs). Свои обрезающие контейнеры потребителя подчиняются тому же правилу; атрибут публичный. Скругление корпуса грида не обрезает кольцо ячейки, потому что ячейки используют внутреннее кольцо.
- **Focus Not Obscured (WCAG 2.2, 2.4.11):** закреплённая шапка и закреплённые колонки грида, а также липкий заголовок группы в списке не закрывают сфокусированный элемент. У скроллера грида `scroll-padding-top` равен высоте шапки, а `scroll-padding-left` — суммарной ширине закреплённых колонок (из store, раздел 10.1). Программная прокрутка к фокусу через виртуализатор учитывает те же величины через `scrollPaddingStart` у `@tanstack/virtual-core`, потому что `scrollToIndex` не опирается на CSS `scroll-padding`. Для пункта списка с липким заголовком группы отступ равен высоте заголовка. Проверяется для ячейки грида и для пункта списка (раздел 12, критерий 7). Вертикаль и горизонталь обеспечиваются по-разному: строки виртуализируются, поэтому вертикально работает `scrollToIndex` с `scrollPaddingStart` на высоту шапки; колонки не виртуализируются, поэтому горизонтально видимость ячейки под закреплённой областью обеспечивают `scroll-padding-left` скроллера и `scrollIntoView({ inline: 'nearest' })` при фокусе ячейки. Учитывает ли `scrollToIndex` опцию `scrollPaddingStart`, по исходнику не проверено: проверяется сценарием критерия 7.

## 6. Виртуализация списков по умолчанию (киллер-фича)

**Виртуализация включена по умолчанию во всех списках кита: Grid, Select, Combobox, MultiSelect и в общем внутреннем ListBox (а значит, и в ContextMenu и меню колонок грида, которые строятся на ListBox начиная с этапа 3).** Её можно только отключить явным пропом `virtualized={false}`; без этого пропа она работает всегда, при любом числе элементов.

- Движок: `@tanstack/solid-virtual` (`createVirtualizer`), одна обёртка в `src/utils/` используется и ListBox, и гридом.
- Высота элементов: стартовая оценка (`estimateSize`) — число в px по правилу раздела 5: вычисленное значение `--s-kit-control-height` на элементе списка, а если оно пустое или не в px, то `--s-kit-control-height-md`, а если и это не разобрать, то 32. Реальная высота измеряется `measureElement`, поэтому строки грида с переносом текста поддерживаются, как в референсе. Оценка ни на что, кроме стартовой раскладки, не влияет.
- В гриде невидимые строки заменяются двумя spacer-строками внутри `<tbody>` (приём из референса): таблица сохраняет семантику `<table>`, `<colgroup>`, sticky-шапку и подвал.
- `overscan` настраивается пропом; значения по умолчанию из референса: 12 для грида, 6 для списков.
- Состояние (выбор, подсветка) хранится по ключу элемента, а не в DOM: строка вне окна рендера остаётся выбранной (так сделано и в референсе).
- Компромисс, который принимается сознательно: поиск браузера (Ctrl+F) не находит строки вне окна рендера.

Порога нет (решение владельца, раздел 2): виртуализатор работает одинаково для списка из 3 и из 100 000 элементов, внутренней оптимизации для малых списков нет. Маленький список и так рендерится целиком, потому что помещается в окно плюс `overscan`. Раскладка ListBox, как и строк грида, строится на spacer-элементах до и после окна рендера, а не на абсолютном позиционировании пунктов: смонтированные пункты остаются в обычном потоке. Ширину панели это не решает (пункты вне окна не измерены), поэтому ширина задаётся политикой ниже.

### 6.1. Контракт навигации в виртуализированном списке

Детали реализации уходят в спек этапа 3; здесь фиксируются инварианты.

- **Три уровня данных:** полный отфильтрованный список элементов → плоский список виртуальных строк (опции плюс заголовки групп) → окно DOM. Индексы относятся только к плоскому списку; связь «ключ элемента ↔ индекс строки» пересчитывается при каждой смене данных или фильтра.
- **Навигация** (ArrowUp/ArrowDown, Home/End, PageUp/PageDown) идёт по полному плоскому списку, пропуская заголовки групп и отключённые опции, а не по смонтированным строкам. Активная опция прокручивается в видимую область через `scrollToIndex`; для строк переменной высоты прокрутка считается завершённой только после измерения целевой строки (при необходимости повторный `scrollToIndex`).
- **Подсветка** хранится по ключу. После смены поискового запроса она сбрасывается на первую допустимую опцию; если подсвеченный ключ исчез из данных, подсветка тоже сбрасывается. Связь фокуса с DOM (`aria-activedescendant` или фокус на строке) указывает только на смонтированный элемент: активная опция всегда находится в окне, потому что навигация прокручивает к ней.
- **Заголовки групп** не активируются и не выбираются. Липкий заголовок текущей группы рендерится отдельно от окна и не исчезает, когда строка заголовка ушла из окна (приём из референса `select-list.tsx`).
- При открытии список прокручивается к выбранному элементу (или к первому, если выбора нет).

### 6.2. Ширина панели и первое измерение

- **Select, Combobox, MultiSelect:** ширина панели равна ширине якоря (`matchReferenceWidth`), но не меньше `--s-kit-listbox-min-width`. Длинные пункты обрезаются многоточием и получают `title`. Так ширина не зависит от того, какие пункты смонтированы.
- **ContextMenu и меню колонок:** ширина в пределах `--s-kit-menu-min-width` … `--s-kit-menu-max-width` измеряется по первому окну рендера и фиксируется, пока меню открыто: прокрутка её не меняет. Длинные пункты обрезаются многоточием с `title`. Обоснование: измерять самый длинный из 100 000 пунктов дорого, а типичное меню целиком помещается в первое окно, так что для него ширина точная.
- **Первое измерение:** панель открывается невидимой (`visibility: hidden`), виртуализатор измеряет первое окно, Floating UI считает позицию, и только после этого панель становится видимой (`visibility: visible` задаётся явно, раздел 8.2). Пользователь не видит прыжка размера или позиции.
- Ширина и позиция считаются от якоря (инициатор или точка клика), а не от хоста панели (раздел 8.1): хост влияет только на наследование стилей и место в DOM.

### 6.3. Критерий производительности

«Плавно» означает воспроизводимый сценарий (рекомендация, уточняется в спеках этапов 3 и 4а): Chrome последней стабильной версии на ноутбуке владельца без троттлинга CPU, production-сборка playground; Select на 100 000 опций и Grid на 100 000 строк × 12 колонок; скрипт страницы равномерно меняет `scrollTop` от начала до конца за 10 секунд (плюс ручная прокрутка колёсиком для визуальной оценки). Цели: открытие Select до 100 мс, во время прокрутки не более 5 % кадров длиннее 16,7 мс по записи Performance-панели, в DOM не больше окна плюс `overscan`.

## 7. Принципы данных и API

- **Controlled/uncontrolled для всех контролов** через общий хелпер:

```ts
function createControllableSignal<T>(options: {
  value: () => T | undefined;      // контролируемое значение из пропсов
  defaultValue: () => T;           // обязательно: начальное значение неконтролируемого режима
  onChange?: (next: T) => void;
}): [get: Accessor<T>, set: (next: T) => void];
```

- `defaultValue` обязателен, поэтому `Accessor<T>` честен: значение есть с первого чтения. Компонент сам подставляет свой дефолт, если пользователь не передал `defaultFoo` (`null` у Select, `false` у Checkbox, пустой `Set` у выбора строк).
- Режим контролируемый, если `value()` не `undefined`. Отсутствие значения поэтому выражается `null` (например, ничего не выбрано в Select), а `undefined` всегда означает «не контролируется».
- В контролируемом режиме `set` только вызывает `onChange`, внутреннее состояние не меняется; в неконтролируемом обновляет внутренний сигнал и вызывает `onChange`.
- **Переходы controlled ↔ uncontrolled не поддерживаются.** Режим фиксируется при первом вычислении. Если потом `value()` становится `undefined`, хелпер продолжает отдавать последнее контролируемое значение; если в неконтролируемом режиме появляется `value()`, оно игнорируется. В обоих случаях в dev-сборке (`import.meta.env.DEV`) выводится `console.warn` с именем компонента, в production — молча.

- **Именование пропсов:** тройка `foo` / `defaultFoo` / `onFooChange`: `value`, `defaultValue`, `onValueChange`; `checked`, `defaultChecked`, `onCheckedChange`; `open`, `defaultOpen`, `onOpenChange`. Имя `onChange` не используется, чтобы не путать с DOM-событием.
- **Общие пропсы контролов:** `size`, `disabled`, `class`, `style`. Все встроенные тексты («Загрузка…», «Нет элементов для отображения») передаются пропами с русскими значениями по умолчанию.
- **Пример формы публичных пропсов** (финализируется в спеке этапа 3):

```ts
interface SelectProps<T> {
  items: readonly T[];
  getKey: (item: T) => string | number;
  getLabel: (item: T) => string;
  renderItem?: (item: T) => JSX.Element;
  groupBy?: (item: T) => string;
  value?: T | null;
  defaultValue?: T | null;
  onValueChange?: (value: T | null) => void;
  open?: boolean;
  defaultOpen?: boolean;
  onOpenChange?: (open: boolean) => void;
  loading?: boolean;
  virtualized?: boolean;            // по умолчанию true
  size?: 'sm' | 'md' | 'lg';
  disabled?: boolean;
  class?: string;
  style?: JSX.CSSProperties;
}
```

- **Грид «глупый»:** получает `rows` (или `groups`), `total`, `loading` и текущие `sort`/`page`, а загрузкой, пагинацией, сортировкой и группировкой данных управляет страница через `onSortChange`, `onPageChange`, `onGroupingChange`, `onRefresh`. UI-состояние (ширины, видимость и закрепление колонок, состав группировки, свёрнутые группы, выбор строк) управляемо по той же схеме `foo` / `defaultFoo` / `onFooChange`, чтобы страница могла сохранять его.
- **Группировка только серверная.** Грид показывает панель группировки (перетаскивание заголовков в панель, чипы, порядок, удаление) и сообщает наружу `onGroupingChange(fields)`; `grouping` — обычная controlled-тройка. Страница перезапрашивает данные и передаёт гриду иерархию `groups: readonly GridGroup<T>[]` (форма в разделе 10.1); плоский `rows` используется только в негруппированном режиме. Свёрнутые группы — controlled-набор ключей групп (`expandedGroupKeys` / `onExpandedGroupKeysChange`). Сам грид строки не группирует и агрегаты не считает.
- **Агрегаты трёх видов, не смешиваются:** групповые (`GridGroup.aggregates`) приходят от сервера и относятся ко всей группе во всём результате запроса; страничные (`pageTotals`) приходят от сервера и относятся к строкам текущей страницы (при пагинации по группам: к группам страницы); глобальные (`totals`) относятся ко всему результату. Страничные и глобальные показываются в `tfoot`: строка «Итого на странице» только если передан `pageTotals`, «Итого по выборке» только если передан `totals`; недостающее не подставляется из другого источника. Ни один вид не пересчитывается по загруженным строкам.
- **Выбор строк по ключам.** `selectedKeys: ReadonlySet<RowKey>` — controlled-тройка (`selectedKeys` / `defaultSelectedKeys` / `onSelectedKeysChange`), выбор сохраняется между страницами. Главный чекбокс управляет только загруженными строками текущей страницы (не окном DOM и не всем серверным результатом); его состояние «все / часть / ничего» считается по ключам этих строк. Массовые операции страница выполняет по `selectedKeys`, а не по смонтированным строкам. «Выбрать весь серверный результат» в первой версии **не поддерживается**. Грид сам выбор не сбрасывает: при смене фильтра или набора данных страница решает сама и при необходимости передаёт пустой набор.
- **Требование к потребителю:** `getRowKey` возвращает ключ, уникальный в пределах результата запроса и стабильный между загрузками (идентификатор записи, а не индекс). Ключи групп (`GridGroup.key`) тоже стабильны между загрузками, иначе свёрнутость групп теряется.
- **Колонки** (рекомендация, подтвердить в спеке этапа 4б): видимость — обычная controlled-тройка с уведомлением на каждое изменение (`onColumnVisibilityChange`), без скрытого черновика внутри грида. Дополнительно `onColumnMenuClose(visibleFields)` сообщает итоговый набор видимых колонок в момент закрытия меню, чтобы страница сама решала, когда перезапрашивать данные (в референсе ребинд делается один раз при закрытии).
- **TanStack Query и любой data-fetching остаются вне кита** (в референсе внутри грида `useQuery` нет). Ни один компонент не делает сетевых запросов. Асинхронные источники подключаются снаружи: страница передаёт `items` и `loading`, а Combobox и MultiSelect сообщают ей введённый текст через `onQueryChange`.

## 8. Позиционирование и оверлеи

- **Хук позиционирования** `createAnchoredPosition` в `src/utils/` поверх `@floating-ui/dom` 1.8.0 (`computePosition`, `autoUpdate`, `offset`, `flip`, `shift`, `size`). Параметры по умолчанию взяты из референса (`use-anchored-popover.ts`): `placement: 'bottom-start'`, `strategy: 'fixed'`, `offset(4)`, `flip({ padding: 8 })`, `shift({ padding: 8 })`, `size({ padding: 8 })` с ограничением `max-height` доступной высотой и опцией `matchReferenceWidth`. `autoUpdate` запускается только пока поповер открыт и снимается в `onCleanup`.
- Для ContextMenu якорем служит виртуальный элемент в точке клика (Floating UI принимает объект с `getBoundingClientRect`); ручное зажатие во вьюпорт из референса (`row-context-menu.tsx`, `column-menu.tsx`) заменяется теми же `flip`/`shift`.
- **Popover** (свой): открытие и закрытие (controllable `open`), dismiss по клику снаружи (нативный слушатель `pointerdown` на `document` в фазе захвата: цель вне якоря и вне панели) и по Esc через стек слоёв.
- **Плавающие панели не переносятся в `body`** (контракт подтверждён владельцем). Панель Popover, Select, Combobox, MultiSelect, ContextMenu и меню колонок монтируется в **хост панели** рядом с инициатором (раздел 8.1) и показывается в top layer через атрибут `popover="manual"` и `showPopover()` (Popover API: Chrome/Edge 114, Firefox 125, Safari и iOS 17). Следствия:
  - CSS-наследование идёт по DOM, поэтому панель получает **все** токены, заданные на хосте и его предках: тему (`color-scheme`), размер, переопределённый primary, компонентные токены вложенной формы. При смене темы или размера на обёртке, пока панель открыта, она обновляется сама, без копирования значений;
  - top layer не обрезается `overflow` предков и не зависит от их z-index; панель, показанная из модального `<dialog>`, оказывается над ним, потому что показана позже;
  - режим `manual` выбран, чтобы браузер не закрывал панели сам (light dismiss): закрытием управляет стек слоёв кита;
  - стандартные стили `[popover]` (рамка, отступы, `inset`, `margin`) сбрасываются в CSS панели; позиционирование — `strategy: 'fixed'` из Floating UI.
- **Что не гарантируется:**
  - наследование от элементов, которые не являются предками **хоста**: токены на соседнем блоке, а также токены, заданные на самом инициаторе или на его промежуточном предке между хостом и инициатором (например, на ячейке или строке грида, на `<label>`). Такие токены нужно задавать на обёртке выше хоста или на самой панели через `class`/`style` её части (`Select.Content`);
  - изоляция от нативных слушателей предков и от их действий по умолчанию (раздел 8.3). В частности, если хост задан вручную через `PanelHostContext` внутри `<label>`, клик по панели активирует контрол этой метки: защищает только автоматический выбор хоста;
  - использование Esc внутри панели для собственных нужд (например, очистка поля поиска в Combobox): Esc перехватывается стеком слоёв в фазе захвата раньше любых обработчиков панели и закрывает верхний слой;
  - работа в браузерах ниже минимальных версий (раздел 2).

  Поведение top layer с `position: fixed`, наследование и изоляция проверяются в приёмке (раздел 12, критерии 5 и 6). Если проверка этапа 0 или 2 провалится, допустимо отступление, записанное в разделе 2.
- **Стек слоёв:** модульный стек открытых слоёв (панели и диалоги в порядке открытия). Esc закрывает только верхний слой; клик снаружи каскадно закрывает слои сверху вниз до слоя, содержащего цель (модальный слой стек не закрывает и каскад на нём останавливается; уточнено в спеке этапа 2, раздел 3.1, 2026-10-30); вложенная панель (Select внутри Dialog, подменю) закрывается, не закрывая родителя. z-index-токены `--s-kit-z-*` нужны только для элементов вне top layer (липкие шапки, лоадер грида).
- **Dialog** строится на нативном `<dialog>` и `showModal()` (модальность, `::backdrop`, инертность фона). Маршрутизация Esc:
  - стек слоёв слушает `keydown` Escape на `document` в фазе захвата. Если верхний слой не диалог, обработчик вызывает `preventDefault()` и закрывает верхний слой; диалог при этом не получает запроса на закрытие;
  - событие `cancel` диалога всегда отменяется (`preventDefault()`), а вместо нативного закрытия Dialog вызывает `onOpenChange(false)`. В контролируемом режиме DOM-диалог закрывается (`close()`) только когда `open` становится `false`; в неконтролируемом — сразу после обновления внутреннего состояния. Так DOM и `open` не расходятся;
  - событие `close`, пришедшее из другого источника (например, `<form method="dialog">`), синхронизируется вызовом `onOpenChange(false)`;
  - браузеры могут не дать отменить `cancel` без пользовательской активации между запросами закрытия (механизм close watcher). Поэтому основной путь — перехват `keydown`, а отмена `cancel` — подстраховка. Поведение проверяется в playground в Chrome, Firefox и Safari.
- **Приёмка Esc:** в Dialog открыт Select; первый Esc закрывает только панель Select, второй Esc закрывает Dialog, `onOpenChange(false)` вызывается ровно один раз; то же для подменю ContextMenu внутри Dialog (три нажатия: подменю, меню, диалог).
- Фокус: при открытии Dialog фокус ставится на первый фокусируемый элемент, при закрытии возвращается на элемент, открывший слой. Ловушка фокуса за пределами того, что даёт `<dialog>`, вне первой итерации.

Разделы 8.1–8.3 — мой анализ рисков решения с Popover API. В браузере он не проверялся; всё проверяется в приёмке (раздел 12, критерий 6).

### 8.1. Хост панели (`PanelHost`)

- Панель монтируется (Solid `<Portal mount={host}>`) не обязательно внутрь инициатора, а в **хост**. Хост по умолчанию — родитель корня компонента-инициатора. Если у инициатора есть предок `table`, `label`, `button`, `a[href]` или `summary`, хостом становится родитель самого внешнего такого предка. Так панель никогда не оказывается DOM-ребёнком `<table>/<tr>/<td>` или интерактивного элемента.
- Хост переопределяется контекстом `PanelHostContext`; ближайший провайдер выигрывает. **Грид задаёт хостом свой корневой элемент вне `<table>`.** Причины: строки и ячейки виртуализированного грида размонтируются при прокрутке, и вместе с ними пропадал бы узел панели; кроме того, панель не может быть ребёнком табличных элементов. Корень грида находится внутри обёртки, которая задаёт токены, поэтому панели грида их получают.
- Хост задаёт только место в DOM и наследование. Позиция и ширина считаются от якоря (раздел 6.2), закрытие — по правилам стека слоёв и раздела 8.4.

### 8.2. Сброс наследуемых свойств на корне панели

Панель в top layer по-прежнему наследует стили от предков хоста. Корень каждой панели явно задаёт из токенов: `font-family`, `font-size`, `font-weight`, `font-style`, `color`, `line-height`, `letter-spacing`, `text-align: start`, `text-indent: 0`, `text-transform: none`, `white-space: normal`, `word-break: normal`, `text-shadow: none`, `cursor: auto`, `visibility: visible`, а главное `pointer-events: auto` (предок может быть под оверлеем загрузки грида или в заблокированном блоке). `user-select` задаётся по смыслу: `none` у меню и списков опций, `text` у Popover с произвольным содержимым.

Кастомные свойства `--s-kit-*` и `color-scheme` намеренно **не сбрасываются**: через них панель получает тему, размер и токены. Шорткат `all: initial` или `all: revert` не используется. По спецификациям CSS Cascade и CSS Variables `all` не затрагивает кастомные свойства, так что токены он не сбросил бы. Но он сбросил бы `color-scheme` в `normal`, и `light-dark()` в панели всегда давал бы светлый вариант; кроме того, сбросились бы `box-sizing`, `display` и прочее. Поэтому только явный список. Утверждение про `all` взято из спецификаций, в браузере не проверялось.

### 8.3. Изоляция событий

Проверено по исходнику `solid-js` 1.9.17 (`web/dist/web.js`):

- обработчики `onClick`, `onDblClick`, `onContextMenu`, `onPointerDown`, `onKeyDown`, `onKeyUp`, `onInput`, `onFocusIn` и других событий из списка `DelegatedEvents` Solid делегирует: один нативный слушатель на `document` в фазе всплытия, а затем ручной обход от `e.target` вверх по `parentNode` с вызовом обработчиков узлов. Обход прекращается, как только обработчик вызвал `stopPropagation()` (проверка `e.cancelBubble`);
- `<Portal>` Solid оборачивает содержимое в `<div>` с полем `_$host`, и делегированный обход из портала **продолжается с логического места портала** (родителя маркера), а не с узла, куда смонтирован портал. Без изоляции клик по опции в панели, смонтированной в корень грида, дошёл бы до делегированных `onClick` и `onDblClick` строки, из которой панель открыта.

Контракт:

- корень панели вешает **делегированные Solid-обработчики** `click`, `dblclick`, `contextmenu`, `pointerdown`, `mousedown`, `keydown`, `keyup`, `input`, `focusin`, `focusout`, которые вызывают `stopPropagation()`. Обработчики внутри панели срабатывают раньше (обход идёт от цели вверх), а обработчики предков и логических предков — нет;
- **нативный** `stopPropagation()` на корне панели **запрещён**: событие не дошло бы до слушателя Solid на `document`, и перестали бы работать делегированные обработчики внутри самой панели, включая пользовательские render props;
- dismiss и Esc от изоляции не страдают: это нативные слушатели на `document` в фазе захвата, они срабатывают раньше любого обхода Solid;
- нативные слушатели предков (`addEventListener`, `on:click`) и действия по умолчанию (`<label>` активирует контрол, Enter отправляет форму) изоляцией не перекрываются. От первого защищает выбор хоста (раздел 8.1): `label`, `button`, `a` и табличные элементы не бывают предками панели. От отправки формы защищают обработчики клавиш кита в панели: Enter и Space, которые они обрабатывают, получают `preventDefault()`.

### 8.4. Панели при прокрутке грида

Правило: контекстное меню строки и меню колонки закрываются при прокрутке грида. Select или другая панель, открытая из ячейки, остаётся открытой, пока её инициатор в окне рендера; когда строка размонтируется, панель закрывается через очистку компонента (`onOpenChange(false)`) без ошибок и без потери фокуса на `body`: фокус переходит на корень грида.

## 10. Целевой API грида и перенос из референса

### 10.1. Целевая форма API (эскиз; подробности в спеке этапа 4)

```ts
type RowKey = string | number;

interface GridColumn<T> {
  id: string;                                // стабильный ключ колонки
  title: string;
  value: (row: T) => unknown;                // значение ячейки по умолчанию
  cell?: (row: T) => JSX.Element;            // рендер ячейки; по умолчанию String(value)
  width?: number;
  minWidth?: number;                         // по умолчанию 60, как в референсе
  locked?: boolean;
  hidden?: boolean;
  sortable?: boolean;
  groupable?: boolean;                       // можно перетащить в панель группировки
  aggregate?: (value: unknown) => JSX.Element; // формат агрегата колонки (групповой или totals)
}

interface GridGroup<T> {
  key: string;                               // стабильный путь группы, например 'status=open/owner=7'
  field: string;                             // id колонки, по которой сгруппировано
  value: unknown;                            // значение группы для заголовка
  count: number;                             // строк в группе во всём результате
  aggregates?: Readonly<Record<string, unknown>>; // по id колонки, от сервера
  children:
    | { kind: 'groups'; items: readonly GridGroup<T>[] }
    | { kind: 'rows'; items: readonly T[] }
    | { kind: 'not-loaded' };                // ленивая подгрузка: раздел 14
}

interface GridProps<T> {
  rows?: readonly T[];                       // негруппированный режим
  groups?: readonly GridGroup<T>[];          // режим группировки (данные от сервера)
  grouping?: readonly string[];
  defaultGrouping?: readonly string[];
  onGroupingChange?: (fields: readonly string[]) => void;
  expandedGroupKeys?: ReadonlySet<string>;
  onExpandedGroupKeysChange?: (keys: ReadonlySet<string>) => void;
  getRowKey: (row: T) => RowKey;             // уникальный и стабильный между загрузками
  columns: readonly GridColumn<T>[];
  total?: number;
  loading?: boolean;
  emptyText?: string;
  sort?: { columnId: string; direction: 'asc' | 'desc' } | null;
  onSortChange?: (sort: GridProps<T>['sort']) => void;   // цикл asc → desc → null
  page?: number;
  pageSize?: number;
  pageSizes?: readonly number[];
  onPageChange?: (page: number, pageSize: number) => void;
  onRefresh?: () => void;
  selectable?: boolean;                                   // колонка чекбоксов массовых операций
  selectedKeys?: ReadonlySet<RowKey>;                     // сохраняется между страницами
  defaultSelectedKeys?: ReadonlySet<RowKey>;
  onSelectedKeysChange?: (keys: ReadonlySet<RowKey>) => void;
  onColumnVisibilityChange?: (visibleFields: readonly string[]) => void;
  onColumnMenuClose?: (visibleFields: readonly string[]) => void;
  onRowDoubleClick?: (row: T) => void;
  rowContextMenu?: (row: T) => readonly MenuItem[];       // MenuItem: тип пункта ContextMenu (этап 2)
  pageTotals?: Readonly<Record<string, unknown>>;         // автосуммы текущей страницы приходят снаружи
  totals?: Readonly<Record<string, unknown>>;             // глобальные автосуммы приходят снаружи
  onEmptyReset?: () => void;                              // кнопка «Сбросить фильтры» в пустом состоянии, только если передан
  virtualized?: boolean;                                  // по умолчанию true
  class?: string;
  style?: JSX.CSSProperties;
}
```

Состояние колонок (ширины, видимость, закрепление, порядок) управляется тройками `foo` / `defaultFoo` / `onFooChange`; точные имена и форма фиксируются в спеке этапа 4. Форма `GridGroup<T>` — эскиз: её финализирует спек этапа 4б вместе с ответом на вопрос раздела 14.

**Серверная группировка — самая объёмная часть этапа 4б и главный риск его размера:** иерархические данные, ленивая подгрузка, виртуализация плоского списка «заголовок → строки → футер» из дерева групп, сохранение свёрнутости между загрузками, согласование с пагинацией. Если этап разрастается, группировка выделяется в отдельный подэтап.

**Корпус грида (инвариант).** Грид — одна карточка с общей рамкой, радиусом и фоном; всё лежит внутри неё:

- верхняя полоса: слева панель группировки (зона перетаскивания и чипы), справа группа из четырёх иконочных кнопок: свернуть группы одного уровня (одна тонкая стрелка вниз), свернуть все (две стрелки вверх), развернуть один уровень (одна вверх), развернуть все (две вниз). Кнопки «Колонки» в полосе нет: видимость, закрепление и «Сгруппировать» живут в меню колонки; полоса идёт первой строкой над шапкой таблицы и отделена тонкой границей, а не вынесена в отдельный блок;
- скроллер с таблицей: закреплённая шапка с плоским фоном `--s-kit-color-surface-2`; в ячейке заголовка слева стрелка сортировки (у неактивной приглушённая), справа кнопка меню колонки из трёх вертикальных точек; тело; итог по группе (строка `gsum` после строк раскрытой группы, у свёрнутой сумма в строке заголовка группы); `tfoot` с двумя строками автосуммы «Итого на странице» и «Итого по выборке» (каждая показывается, только если передан её источник: `pageTotals` и `totals`, раздел 7);
- нижняя полоса: слева пейджер («в начало», «назад», номера страниц, «вперёд», «в конец») и сразу за ним селект размера страницы; справа по порядку сводка «Записей … из …» и кнопка обновления.

**Состояния грида.** Загрузка: рамка, панель группировки и шапка на месте, строки заменены заглушками (пульсация прозрачности, без градиентов), под панелью бегущая полоса прогресса (`role="progressbar"`), значок обновления вращается, пейджер недоступен, `aria-busy="true"`. Минимум доступности состояний: у `progressbar` есть имя (проп `loadingLabel`, по умолчанию «Загрузка»); результат загрузки («Найдено N записей» или «Ничего не найдено») объявляется скрытой областью `aria-live="polite"` вне занятой области; при замене строк заглушками фокус, находившийся внутри строки, переносится на корень грида. Пусто: тело заменено блоком по центру (иконка, «Ничего не найдено», пояснение; кнопка «Сбросить фильтры» только если передан `onEmptyReset`, фильтрами владеет страница), шапка и нижняя полоса остаются. Список Select, Combobox, MultiSelect: «Ничего не найдено» при пустом результате поиска и «Список пуст» при отсутствии данных. Анимации отключаются при `prefers-reduced-motion`.

Корпус обрезает содержимое по скруглению (`overflow: clip`) и ставит `data-s-kit-focus-inset`, поэтому все фокусируемые элементы полос и ячеек используют внутреннее кольцо (раздел 5.1). Когда группировка выключена (`groupable={false}`) и тулбар пуст, верхней полосы нет.

**Раскладка таблицы (инвариант).** Единственный источник фактической ширины колонок — ширины в store. Таблица использует `table-layout: fixed`; ширина `<table>` вычисляется явно как сумма ширин видимых колонок плюс служебная колонка чекбоксов (если `selectable`) плюс добор последней колонки; каждая `<col>` получает ширину из store. Рамки и внутренние отступы ячеек входят в ширину колонки из store; как именно это достигается в фиксированной табличной раскладке (модель рамок таблицы, где рисуется разделитель), решает спек этапа 4а, а приёмка ниже подтверждает, что сумма не расходится с DOM. Spacer-строки состоят из одной ячейки с `colspan` на все колонки и на ширины не влияют. Sticky-смещения закреплённых колонок считаются из тех же ширин. Содержимое ячеек на ширину не влияет: длинный текст переносится или обрезается. **Приёмка:** длинное содержимое, появляющееся при прокрутке; горизонтальная прокрутка с закреплёнными колонками; скрытие и показ колонок; ресайз закреплённой и обычной колонки — без наложений и зазоров между sticky-ячейками. Корпус: рамка и скругление общие для верхней полосы, таблицы и нижней полосы; углы не прорезаются содержимым; кольцо фокуса у чипа группировки, кнопки тулбара, ячейки в углу и кнопки пейджера видно целиком внутри рамки. Тип строки `T` выводится из `rows`, `getRowKey` заменяет жёсткий `row.Id`, `columns` заменяет константу `COLUMNS`, `cell` заменяет `formatCell` и шаблоны метаданных.

### 10.2. Таблица переноса

Пропсы не деструктурируются (иначе теряется реактивность): `splitProps`/`mergeProps`.

## 11. Конвенции кода

- **Один класс — один файл.** Два класса в одном файле недопустимы, включая вложенные DTO, схемы конфигов и классы ошибок: каждый в своём файле с именем по классу в kebab-case, связанные классы импортируют друг друга. В компонентном коде классов почти не будет, но правило действует и проверяется на ревью.
- Имена файлов и папок в kebab-case: `context-menu.tsx`, `create-controllable-signal.ts`.
- **Один компонент — своя папка** в `src/components/` с `index.ts` (только реэкспорт публичного), `<имя>.tsx`, `<имя>.module.css`, при необходимости `<имя>.test.tsx` и чистые функции в отдельных `.ts`.
- Компоненты экспортируются именованно, без `export default`. Имя подпути совпадает с именем папки.
- Компоненты импортируют друг друга через относительные пути внутри `src/`, а не через `@stark/solid-kit/...`.
- Логика (группировка, сортировка, вычисление видимых строк, ширины колонок, номера страниц, даты) живёт в чистых функциях без DOM и покрывается юнит-тестами.
- Пропсы не деструктурируются; значения по умолчанию через `mergeProps`, проброс атрибутов через `splitProps`.
- Минимум a11y, который закладывается сразу: нативные `<button>`, `<input>`, `<label>`, `<table>`, `<dialog>`; `type="button"` у кнопок; `aria-expanded` у триггеров, `aria-sort` у заголовков грида, `aria-label` у иконочных кнопок; Esc закрывает слои; стрелки и Enter в открытом списке. Всё остальное не цель первой итерации.
- Линтинг: `@stark/eslint-config` и `@stark/stylelint-config`; линтер и `tsc --noEmit` проходят без ошибок перед каждым тегом.
- **Репозиторий публичный: секреты не коммитятся.** Ключи, токены, пароли, `.env*`, бэкапы и локальные конфиги с учётными данными не попадают в коммиты, теги и сообщения коммитов. С первого коммита в `.gitignore` есть `.env*`, `*.pem`, `*.key`, `.npmrc` с токенами и каталоги бэкапов. Кит не требует ни одного секрета: git-зависимость ставится анонимно. Перед тегом вывод `git diff` и список файлов тега просматриваются на секреты.
- **Кольцо фокуса только через токены и в двух вариантах** (раздел 5.1): `:focus-visible` + `outline` из `--s-kit-focus-*` и `--s-kit-color-focus-ring`; внутренний вариант включается атрибутом `data-s-kit-focus-inset` на обрезающем контейнере, а не локальными правилами компонента; `box-shadow` в роли индикатора фокуса и `outline: none` без замены запрещены.
- **В компонентном CSS запрещены литералы цветов** (hex, `rgb()`, `hsl()`, `oklch()` и т. п., именованные цвета): только токены, а состояния вычисляются через `color-mix()` от токена в `tokens.css`. Литералы допустимы только в базовых токенах `tokens.css`. *Предложение* по автоматической проверке: в конфиге stylelint кита поверх `@stark/stylelint-config` секция `overrides` для `src/components/**/*.module.css` с правилами `color-no-hex: true`, `color-named: 'never'` и `function-disallowed-list: ['rgb', 'rgba', 'hsl', 'hsla', 'hwb', 'lab', 'lch', 'oklab', 'oklch', 'color']`. Конфиг собирается и проверяется на этапе 0 (поведение `color-named` с `transparent` и `currentColor` уточняется там же).
- **Семантика списков разделена.** Общий движок списка (виртуализация, навигация, подсветка, раздел 6.1) не прошивает ARIA-роли; роли задаёт слой над ним. Выбор значений (Select, Combobox, MultiSelect): `role="listbox"`, `role="option"`, `aria-selected`. Команды (ContextMenu, меню колонок): `role="menu"`, `role="menuitem"`, без `aria-selected`; активация пункта вызывает команду и закрывает меню, а не выбирает значение. Полный ARIA-паттерн меню и списков в первую итерацию не входит.
- Корневой элемент каждого компонента и каждой плавающей панели несут атрибут `data-s-kit` (раздел 4).
- **Каждый этап в своём спеке явно перечисляет применённые паттерны и границы абстракций** (какие интерфейсы, кто от кого зависит); это проверяется на ревью.

### 11.1. Архитектурные паттерны и принципы

Правило применения: паттерн вводится, когда решает конкретную проблему этого кита, и записывается в спеке этапа. Абстракции ради паттерна не создаются (YAGNI).

**Compound components.** Сложные компоненты собираются из частей с общим состоянием в контексте:

```tsx
<Select.Root value={value()} onValueChange={setValue} items={users} getKey={(u) => u.id}>
  <Select.Trigger placeholder="Сотрудник" />
  <Select.Content>
    <Select.Group label="Отдел продаж">
      <Select.Option item={user} />
    </Select.Group>
    <Select.Empty>Никого не нашли</Select.Empty>
  </Select.Content>
</Select.Root>
```

- `Select.Root` создаёт состояние (`createControllableSignal`, подсветка, открытие) и отдаёт его через `createContext`/`useContext`; части читают только нужные им поля. Контекст без провайдера бросает понятную ошибку («Select.Option вне Select.Root»).
- Каждая часть в своём файле внутри папки компонента (`select-root.tsx`, `select-trigger.tsx`, `select-context.ts`, ...). `index.ts` собирает namespace: `export const Select = Object.assign(SelectQuick, { Root, Trigger, Content, Option, Group, Empty })`, где `SelectQuick` — быстрая форма `<Select items={...} />` из раздела 7, построенная поверх тех же частей (фасад, не замена). JSX Solid поддерживает теги вида `<Select.Trigger>`.
- Tree-shaking: части одного компонента связаны через один объект и попадают в бандл вместе, как только импортирован подпуть `@stark/solid-kit/select`. Между компонентами tree-shaking не страдает: каждый подпуть это отдельный граф модулей, и неимпортированный `grid` в бандл не попадает (критерий приёмки 1, раздел 12).
- Когда что: плоские компоненты — Button, IconButton, Input, NumericInput, Switch, Checkbox, Radio, Field, ButtonGroup (решение 2026-10-29, спек этапа 1, раздел 3.4: части это готовые Button, общего состояния нет). Compound — Select, Combobox, MultiSelect, Dialog, Tabs, ContextMenu, ToggleGroup, RadioGroup, части грида (панель группировки, пейджер, меню колонок). Критерий: у компонента больше одной самостоятельно размещаемой области или пользователь должен вставлять свою разметку между частями.

**Render props.** Слоты для своей разметки: `renderOption`, `renderValue`, `renderGroupHeader` у списков, `cell` у колонки грида, children-как-функция там, где нужно состояние:

```ts
renderOption?: (item: T, state: { selected: Accessor<boolean>; active: Accessor<boolean> }) => JSX.Element;
children?: JSX.Element | ((state: { open: Accessor<boolean>; close: () => void }) => JSX.Element);
```

- Состояние передаётся аксессорами, а не значениями: render-функция вызывается один раз на элемент внутри `<For>`, а изменения подхватываются точечно, без повторного рендера.
- Пропсы не деструктурируются; `splitProps` отделяет свои пропсы от проброшенных атрибутов, `mergeProps` задаёт значения по умолчанию.
- **Контракт выполнения слотов** (`renderOption`, `renderValue`, `cell`): кит вызывает функцию из JSX элемента (внутри отслеживаемой области, не в теле компонента) и по умолчанию один раз на элемент. Реактивные чтения внутри *возвращаемого JSX* (`{state.selected() ? <A /> : <B />}`) Solid привязывает точечно, функция повторно не вызывается. Реактивные чтения в теле функции вне JSX подписывают сам вызов: он повторится и пересоздаст разметку, поэтому состояние читается внутри JSX. Пример: `renderOption={(item, s) => <span>{s.selected() ? '✓ ' : ''}{item.name}</span>}`: при смене `selected` обновится только текстовый узел.
- Функция-ребёнок отличается от обычных детей по `typeof children === 'function' && children.length > 0` и вызывается через `untrack` один раз при создании (как это делают `Show` и `Match` в Solid); реактивные чтения состояния (`open()`) делаются внутри её JSX. Хелпер `children()` применяется только к обычным детям: он сам вызывает функции без аргументов и сломал бы функцию-ребёнка.

**SOLID в применении к киту:**

- **SRP:** логика, состояние и разметка разделены. Для грида: чистые функции (`flattenGroups` — дерево `GridGroup<T>` в плоский список строк, расчёт ширин, `getPageItems`), хуки (`createColumnResize`, `createGroupingDrag`, `createRowSelection`), компоненты (только разметка и связывание). У каждого одна причина для изменения.
- **OCP:** расширение без правки исходников кита: токены, `class`/`style`, render props и compound-части. Новая доменная ячейка грида — это `cell` у колонки, а не ветка внутри грида.
- **LSP:** контролы значений соблюдают единый контракт (`value`/`defaultValue`/`onValueChange`, `disabled`, `size`, `class`, `style`), поэтому Field и формы работают с любым из них, а Select и Combobox взаимозаменяемы в одном месте формы.
- **ISP:** маленькие контексты и узкие пропсы. Контекст Select делится на «состояние выбора» и «состояние панели»; Select не знает про настройки виртуализации ListBox, наружу торчит только `virtualized`.
- **DIP:** ListBox и грид зависят от интерфейса окна рендера (`items()`, `totalSize()`, `measure(el)`, `scrollToIndex(i)`), а не от TanStack напрямую. Реализаций две: на `createVirtualizer` и «всё сразу» для `virtualized={false}`. Оверлеи зависят от интерфейса позиционирования, за которым стоит `@floating-ui/dom`.

**GoF — только то, что реально ложится на кит:**

- **Observer:** уже реализован сигналами и эффектами Solid; своей шины событий не пишем.
- **Strategy:** фильтр и сравнение опций Combobox (`filter?: (item, query) => boolean`), реализация окна рендера (DIP выше), опции позиционирования.
- **Composite:** дерево пунктов ContextMenu с подменю; дерево групп грида (группа содержит группы или строки).
- **Template Method / хук-колбэки:** общий жизненный цикл слоя (открыть → позиционировать → слушать dismiss → закрыть → вернуть фокус) в Popover; Dialog и ContextMenu подключаются колбэками `onOpenChange`, `onDismiss`, а не наследованием.
- **Adapter:** преобразование ISO-строк дат во внутреннее представление календаря и обратно; обёртка над `@floating-ui/dom` и над `@tanstack/solid-virtual`.
- **Facade:** быстрые формы (`<Select items>`) поверх compound-частей.
- **Decorator (композиция хуков):** поведение наращивается комбинацией маленьких хуков (`createDismiss` + `createAnchoredPosition` + `createLayer`), а не обёртками-компонентами.
- **State:** открытие и выбор — явные небольшие наборы состояний в сигналах; конечный автомат вводится, только если в спеке этапа доказано, что без него логика запутывается (кандидат — drag-and-drop группировки).
- **Factory:** создание стандартных колонок грида (`checkboxColumn()`, `numberColumn()`), если на этапе 4 появится повторяющаяся конфигурация.
- **Не применяем:** Singleton и глобальный стор (состояние живёт в компонентах и контекстах; исключение — стек слоёв, это модульное состояние с одной ответственностью), Visitor, Abstract Factory, Command с undo-стеком, собственные event bus и DI-контейнеры: проблем, которые они решают, в ките нет.

**Карта паттернов по компонентам:**

| Компонент | Паттерны |
|---|---|
| Grid | compound (панель группировки, пейджер, меню колонок), render props (`cell`, `aggregate`), Composite (дерево `GridGroup<T>`), DIP (окно рендера), SRP (функции / хуки / разметка) |
| Select / Combobox / MultiSelect | compound + Facade (быстрая форма), render props (`renderOption`, `renderValue`), Strategy (фильтр), DIP (окно рендера, позиционирование) |

## 12. Тестирование и playground

- **Юнит-тесты** (Vitest) на чистые функции: `createControllableSignal` (включая предупреждения о смене режима), разворачивание дерева групп в плоский список, навигация по плоскому списку (раздел 6.1), ширины колонок, номера страниц, вычисления дат.
- **Компонентные тесты** (`@solidjs/testing-library`) на поведение: controlled/uncontrolled, открытие и закрытие слоёв, выбор в списках, навигация за пределы окна. В jsdom нет раскладки, а одного `initialRect` недостаточно, поэтому интерфейс окна рендера (раздел 11.1, DIP) получает **тестовый адаптер геометрии и прокрутки**: известные размеры строк, управляемые вручную наблюдения размера и смещения, программный scroll offset, числовая оценка высоты без чтения CSS. Точки подключения в `@tanstack/virtual-core` 3.19.8 (проверено по исходнику): `observeElementRect`, `observeElementOffset`, `scrollToFn`, `measureElement`, `estimateSize`, `initialRect`, `initialOffset`. Реальная геометрия (измерение переменных высот, sticky, top layer) проверяется только в браузере, в playground.
- **playground/** это Vite 8-приложение в workspace: страница на компонент, состояния прямо в JSX, переключатель темы (системная / светлая / тёмная через `data-s-kit-theme`), поле для своего primary и переключатель размера (`data-s-kit-size` на корне страницы). Отдельные страницы: «Контролы в ряд» (раздел 5), «Темы» (раздел 4, критерий 5), «Панели» (раздел 8, критерий 6), «Фокус в контейнерах с overflow» (раздел 5.1, критерий 7), переключатель примера палитры (Мята как рабочая, Синий как другой оттенок, Моно как проверка нейтральной палитры) и «Большие списки» (Select и Grid на 100 000 элементов).
- Storybook не используется. `storybook-solidjs-vite@10.7.4` поддерживает Vite 8, поэтому его можно добавить позже поверх тех же компонентов; компоненты от него не зависят.

3. Страница «Контролы в ряд» проходит проверку высот во всех пяти рядах (раздел 5).
4. Страница «Большие списки» выполняет сценарий и цели раздела 6.3.
5. Страница «Темы» в Chrome, Firefox и Safari минимальных версий (раздел 2) показывает: системная тема подхватывается без атрибута; `data-s-kit-theme` на обёртке переключает тему только внутри неё; `--s-kit-color-primary`, переопределённый на обёртке, перекрашивает hover, фокус-кольцо, подсветку опции и выбранную строку; `light-dark()` внутри `color-mix()` в кастомных свойствах разрешается по теме элемента. Сценарий вложенных областей: тёмная обёртка `sm` с переопределённым primary, внутри форма со своим компонентным токеном `--s-kit-select-bg`, внутри Select — его панель (в top layer) получает тему, размер, primary и `--s-kit-select-bg`; то же внутри Dialog; смена темы и размера обёртки при открытой панели сразу отражается на панели. Hover и active основной кнопки заметно отличаются от покоя на палитрах Мята, Синий и Моно (Моно проверяет худший случай: primary почти равен цвету текста) в светлой и тёмной теме, контраст текста кнопки в каждом состоянии не ниже 4,5:1 (раздел 4.1); полупрозрачный материал панели и его сплошной запасной фон дают контраст текста не ниже 4.5:1 (раздел 4.3).
6. Страница «Панели» в Chrome, Firefox и Safari минимальных версий (разделы 8.1–8.4; ни один сценарий в браузере ещё не проверялся):
   - (а) Select и ContextMenu, открытые из ячейки грида с `text-align: right`, `white-space: nowrap` и `overflow: hidden` на ячейке и таблице: панель не обрезана, не унаследовала выравнивание и перенос, шрифт и цвет из токенов;
   - (б) панель, инициатор которой лежит под предком с `pointer-events: none` (оверлей загрузки, заблокированный блок), остаётся кликабельной;
   - (в) Select внутри `<label>` и внутри кликабельной карточки или строки грида с `onClick`/`onDblClick`: клик и двойной клик по опции не активируют `<label>` и не вызывают обработчики строки или карточки; Enter в панели внутри `<form>` не отправляет форму;
   - (г) прокрутка виртуализированного грида при открытой панели: контекстное меню строки и меню колонки закрываются; Select из ячейки остаётся открытым, пока строка в окне, и закрывается без ошибок, когда строка размонтирована;
   - (д) предки инициатора с `transform`, `filter`, `contain: paint` и `overflow: hidden`: панель не обрезана и позиционирована у якоря (`position: fixed` в top layer);
   - (е) фокус в панелях: активный пункт ListBox, ContextMenu и меню колонок показывает внутреннее кольцо целиком у верхнего и нижнего края прокручиваемого списка; кольцо пункта не закрыто липким заголовком группы; после закрытия панели фокус и внешнее кольцо возвращаются на инициатор.
7. Страница «Фокус в контейнерах с overflow» в Chrome, Firefox и Safari минимальных версий (раздел 5.1; в браузере не проверялось):
   - каждый интерактивный компонент кита стоит вплотную к краю четырёх контейнеров: `overflow: hidden`, `overflow: auto`, `overflow: clip`, `border-radius` + `overflow: hidden`, а также внутри контейнера с `data-s-kit-focus-inset`;
   - встроенная проверка по каждому компоненту: `focus()` с клавиатурной модальностью, затем сравнение прямоугольника кольца (прямоугольник элемента, расширенный на offset и width для внешнего варианта или равный ему для внутреннего) с прямоугольником ближайшего обрезающего предка; отклонения выводятся на страницу. Эта проверка вспомогательная: она сравнивает с ближайшим обрезающим предком и не ловит обрезку дальним предком, скруглённым углом и перекрытие липким элементом, поэтому проверка идёт по цепочке всех обрезающих предков, а глазами проверяются сценарии углов (скруглённый контейнер, элемент в углу) и перекрытий (липкая шапка, липкий заголовок группы);
   - сценарий Focus Not Obscured: при навигации клавиатурой по гриду сфокусированная ячейка не уходит под закреплённую шапку и закреплённые колонки при прокрутке вверх, вниз и влево; пункт списка не уходит под липкий заголовок группы.

## 14. Открытые вопросы

1. **Пагинация при серверной группировке и ленивая подгрузка групп (этап 4б).** Варианты: (а) страницы считаются по строкам, и группа может продолжаться на следующей странице; (б) страницы считаются по группам верхнего уровня, а строки внутри развёрнутой группы подгружаются лениво (`children.kind === 'not-loaded'` → событие `onGroupExpand(key)` → страница догружает строки). Рекомендация: (б). Группа не разрезается между страницами, агрегаты и счётчик в заголовке всегда относятся к целой группе, а ленивая подгрузка сочетается с виртуализацией, потому что свёрнутые группы не требуют строк. Цена: пейджер показывает число групп верхнего уровня, а не строк, и для больших групп нужна пагинация или виртуализированная подгрузка внутри группы. Решение принимается в спеке этапа 4б.

2. **Колонки: уведомления об изменении видимости (этап 4б).** Рекомендация: `onColumnVisibilityChange` на каждое изменение плюс `onColumnMenuClose(visibleFields)` при закрытии меню колонки, чтобы страница сама решала, когда перезапрашивать данные. Решение принимается в спеке этапа 4б.
3. **Лицензия репозитория.** Репозиторий публичный, а файла `LICENSE` в спеке нет. Без лицензии код по умолчанию закрыт для использования другими, но владельцу как единственному потребителю это не мешает. Варианты: MIT (разрешительная, привычная), без лицензии (все права сохранены). Решение нужно до первого пуша.
4. **Создание и публикация репозитория на GitHub.** Локальный репозиторий не отправлен никуда. Нужно решение: когда создавать `StarkElessar/solid-kit` и пушить; публичным он становится в момент пуша, и всё, что уже закоммичено (включая документы в `docs/`), станет видно всем. Рекомендация: перед пушем одна проверка истории на секреты.
5. **Второй независимый просмотр спека моделью Astra (закрыт 2026-10-29).** Вердикт «доработать», 15 замечаний; каждое проверено по тексту спека, часть подтверждена измерением в браузере. Внесено: контраст hover/active (№1, подтверждено измерением, решение владельца: вопрос 7), кольцо фокуса на заливке (№2, требование этапа 1, раздел 5.1), граница флажка 50 % и граница полей (№3, вопрос 8), источник `pageTotals` (№4), исполнимое правило материала (№5, раздел 4.3), контракт состояний грида (№6), критерий 7 как вспомогательная проверка (№7), горизонтальный фокус (№8), пример токенов синхронизирован с Синей палитрой (№9), критерии привязаны к этапам (№10), обязательный минимум доступности (№11), определение «N из M» (№12), контракт слотов (№13), оболочка группы кнопок (№14), `tint` определён и палитра Моно для проверки задана в playground (№15).
