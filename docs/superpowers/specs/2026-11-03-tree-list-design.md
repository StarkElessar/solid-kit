# TreeList: дизайн

Дата: 2026-11-03. Статус: черновик на просмотр владельцу. Этап: без номера (новая подсистема после этапа 5).

## 1. Цель и границы

TreeList это иерархическая таблица: тот же грид, но строки образуют дерево, и дерево всё время разворачивается и сворачивается. Нужен для замены Kendo TreeList, который лагает на списках больше 1000 записей.

Входит:
- дерево из плоского списка с `parentKey` (основной сценарий BackOffice) и из ленивой подгрузки детей (второй вариант);
- виртуализация (десятки тысяч узлов без лагов);
- закрепление колонок слева, ресайз, скрытие колонок, меню колонки, выбор строк, сортировка, пустое состояние и скелетон, контекстное меню строки, автосуммы: всё как в гриде;
- верхняя полоса с четырьмя кнопками уровней справа;
- нижняя полоса: пейджер и кнопка «Обновить».

Не входит (решение владельца и YAGNI):
- группировка (панель с чипами, пункт «Сгруппировать», перетаскивание заголовков);
- перетаскивание узлов, редактирование в ячейках, вставка и удаление узлов;
- стрелочная навигация по строкам (в гриде её нет; появится в обоих компонентах одной задачей позже);
- серверное дерево с подгрузкой страницами внутри узла.

## 2. Главный принцип: общее строго переиспользуется

Решение владельца (2026-11-03): всё, что TreeList делит с гридом, живёт в одном экземпляре. Копировать файлы грида в `tree-list/` нельзя, повторять их логику нельзя. Расхождение вида или поведения общей части между двумя компонентами считается дефектом.

Как это обеспечивается:

1. **Движок грида выделяется в `GridBase`** (внутренний компонент в `src/components/grid/`, в публичный индекс не экспортируется). Всё тело текущего `Grid` (состояния колонок, ресайз, окно рендера, выбор, сортировка, меню, футер, живая область, группировка) переезжает в него без изменения поведения, `Grid` становится тонкой оболочкой, которая отдаёт ему свои пропсы. Дерево подключается к движку одним внутренним пропсом `tree` (`GridTreeSource`: плоский список видимых узлов, действия раскрытия, подписи). `TreeList` тоже оболочка: держит раскрытость и ленивую догрузку, строит плоский список из дерева и отдаёт его движку. Групповая логика остаётся в движке (выносить её в оболочку `Grid` не нужно: это лишний риск без пользы). Существующие тесты грида (`grid.test.tsx`, больше 1900 строк) без правок обязаны остаться зелёными: это страховка рефакторинга.
2. **Каждая общая часть остаётся одним файлом, в `tree-list/` её нет.** Общие файлы: `GridTable`, `GridColgroup`, `GridHeader`, `GridHeaderCell`, `GridSortButton`, `GridColumnMenuButton`, `GridColumnMenu`, `GridResizeHandle`, `GridBody`, `GridRow`, `GridCell`, `GridSelectCell`, `GridSelectHeaderCell`, `GridSkeleton`, `GridEmpty`, `GridProgress`, `GridLiveRegion`, `GridRowMenu`, `GridTotals`, `GridFooter` (обёртка над `Pager`), `GridToolbarButton`, `createVirtualWindow`, `createGridResize`, `computeColumnLayout`, `applyColumnState`, `selection-state`, CSS-модуль `grid.module.css`.
3. **Четыре кнопки уровней становятся общим `GridLevelToolbar`.** Сейчас `GridGroupingToolbar` берёт обработчики и подписи из контекста грида группировки. Он переименовывается в `GridLevelToolbar` и получает обработчики пропсами (`onCollapseLevel`, `onCollapseAll`, `onExpandLevel`, `onExpandAll`, `disabled`, `labels`). Значки, размеры (24 px, muted), порядок (свернуть уровень, свернуть все, развернуть уровень, развернуть все) остаются в этом одном файле. Грид и TreeList вставляют его в полосу `GridBar` (бывшая `GridGroupingBar`, см. ниже).
4. **Верхняя полоса `GridBar` общая.** Слева слот (в гриде панель группировки, в TreeList пусто), справа `GridLevelToolbar`. Стили `.bar` и `.toolbar` в `grid.module.css` без изменений.
5. **Шеврон узла и шеврон группы это один компонент `GridChevron`** (14 px, путь `M6 4l4 4-4 4`, поворот на 90° у раскрытого). Сейчас `Chevron` объявлен внутри `grid-group-row.tsx`; выносится в свой файл, группа и узел импортируют его. Кнопка-шеврон (`GridExpander`: `<button>` с `aria-expanded` и `aria-label`) тоже одна на оба компонента; клик по интерактивной цели строка тела и так игнорирует.
6. **Отступ уровня общий.** Токен `--s-kit-grid-indent` (16 px на уровень) и логика расчёта `level * 16` в одной функции `indentOf(level)`; строка группы, строка данных под группой и узел дерева используют её.
7. **Подписи уровней общие.** `collapseLevel`, `collapseAll`, `expandLevel`, `expandAll` и подписи шеврона `expand(title)`, `collapse(title)` выносятся из `GridGroupingLabels` в `GridLevelLabels` (дефолты те же); `GridGroupingLabels` расширяет их. TreeList принимает `levelLabels`.
8. **Проверка единства**: в `tree-list/` не должно быть ни одного `.module.css` и ни одного файла, дублирующего имя из грида. Это проверяет тест-страж (раздел 10).

Мерило успеха принципа: удаление `src/components/tree-list/` не оставляет в гриде мёртвого кода, а правка любого общего файла видна в обоих компонентах.

## 3. Публичный API

```ts
export interface TreeListProps<T> extends TreeListSharedProps<T> {
	/** Плоский список узлов целиком. Дерево строится по `getParentKey`. Взаимоисключает `loadChildren`. */
	rows?: readonly T[];
	/** Ключ родителя; `undefined` и `null` у корневых узлов. Родителя нет в списке: узел считается корневым. */
	getParentKey?: (row: T) => RowKey | null | undefined;
	/** Ленивый режим: корни приходят в `rows`, дети узла загружаются при раскрытии. */
	loadChildren?: (row: T) => void;
	/** Есть ли у узла дети. Нужен в ленивом режиме, в обычном дети известны из `rows`. */
	hasChildren?: (row: T) => boolean;
	expandedKeys?: ReadonlySet<RowKey>;
	defaultExpandedKeys?: ReadonlySet<RowKey>;
	onExpandedKeysChange?: (keys: ReadonlySet<RowKey>) => void;
	/** Ключи узлов, дети которых сейчас догружаются (ленивый режим): под узлом строка «Загрузка…». Выставляется синхронно в `loadChildren`. */
	loadingKeys?: ReadonlySet<RowKey>;
	levelLabels?: Partial<GridLevelLabels>;
}
```

`TreeListSharedProps<T>` это `GridProps<T>` без `groups`, `groupable`, `grouping`, `defaultGrouping`, `onGroupingChange`, `groupSort`, `defaultGroupSort`, `onGroupSortChange`, `expandedGroupKeys`, `defaultExpandedGroupKeys`, `onExpandedGroupKeysChange`, `onGroupExpand`, `groupingLabels`, `rows`. Тип выводится из `GridProps` через `Omit`, пропсы не переписываются: добавление пропса в грид автоматически доступно в TreeList.

Два варианта подключения (решение владельца: «2 варианта, чтобы они легко подключались/выбирались»):

- **Плоский список (по умолчанию).** `rows` + `getRowKey` + `getParentKey`. Так живёт BackOffice: Kendo получает весь список целиком с `Id/ParentId`. Дерево строит и разворачивает клиент. Для документов, где у BackOffice `FakeId/FakeParentId`, страница передаёт эти поля в `getRowKey` и `getParentKey`.
- **Ленивая подгрузка.** `rows` (корни) + `hasChildren` + `loadChildren`; страница кладёт загруженных детей в `rows` (те же плоские строки с `parentKey`) и на время запроса держит ключ родителя в `loadingKeys`. TreeList вызывает `loadChildren(row)` один раз при первом раскрытии узла, у которого в `rows` ещё нет детей. Повторное раскрытие использует уже загруженное.

Дерево рисуется в первой видимой колонке (так же, как отступ строк под группой в гриде); отдельного пропса колонки дерева нет. Выбор варианта определяется наличием `loadChildren`, отдельного флага нет. Оба варианта используют один и тот же `flattenTree`, ленивость лишь добавляет строку-заглушку и вызов колбэка.

Выбор строк и автосуммы: `selectable`, `selectedKeys` и прочее работают как в гриде, ключ `getRowKey` общий. Выбор узла не выбирает потомков (каскад не нужен: BackOffice его не использует; при необходимости добавляется позже отдельным пропсом).

## 4. Данные и алгоритмы

### 4.1. `flattenTree`

`flattenTree(rows, getRowKey, getParentKey, expanded, loadingKeys?) → { items, rows }` строит плоский список видимых узлов в порядке «родитель, затем его дети». Результат использует те же `GridItem`, что и грид:

- `row` получает необязательное поле `node`: `{ key: RowKey; expandable: boolean; expanded: boolean }` и `level` (уже есть у вида `row`). Строка без `node` это строка грида; значит, `GridRow` один на оба компонента, а шеврон в нём рисуется, только если есть `node`.
- `loading` (уже есть у вида) используется как строка «Загрузка…» под раскрытым узлом из `loadingKeys`, `key` это ключ родителя.
- вида `group` и `footer` в дереве нет.

Сложность: индекс «родитель → дети» строится один раз при смене `rows` за O(n) и кешируется через `createMemo`; смена `expandedKeys` только заново обходит видимую часть за O(видимых узлов). Узел раскрыт и виден, только если раскрыты все его предки. Цикл в данных (узел сам себе предок) обрывается: узел в цикле считается корнем, наружу не бросается исключение, `console.warn` в dev-режиме.

Порядок детей это порядок в `rows` (сортирует страница, как в гриде: TreeList не сортирует). Сортировка применяется страницей на каждом уровне.

### 4.2. Кнопки уровней

Семантика та же, что у BackOffice (`_ExpandCollapseButtonsTreeList.cshtml`) и у групп грида; функции чистые и покрываются юнит-тестами:

- `collapseTreeLevelKeys`: сворачивает раскрытые видимые узлы наибольшей глубины; нечего сворачивать, возвращается тот же набор (ссылка не меняется, колбэк не вызывается).
- `expandTreeLevelKeys`: раскрывает свёрнутые видимые узлы наименьшей глубины среди видимых, у которых есть дети.
- `collapse all`: пустой набор.
- `expand all`: ключи всех узлов с детьми (в ленивом режиме только уже загруженных; незагруженные раскрываются по одному и догружаются при показе).

Кнопки недоступны, пока идёт загрузка (`loading`) и когда дерево пустое.

### 4.3. Ленивая догрузка

Раскрытый видимый узел с `hasChildren(row) === true`, у которого в данных нет детей и для которого `loadChildren` ещё не вызывался, получает строку `loading` («Загрузка…», спиннер как в макете). При монтировании строки TreeList запоминает ключ как запрошенный и вызывает `loadChildren(row)` один раз; страница обязана синхронно положить ключ в `loadingKeys`, пока идёт запрос. Строка есть, пока ключ в `loadingKeys`. Запрошенный ключ забывается, когда узел сворачивается: повторное раскрытие узла, дети которого так и не пришли, запрашивает их заново. Вызов идёт из монтирования строки, а не из клика, поэтому «развернуть уровень» догружает так же, как шеврон. «Развернуть все» раскрывает только узлы, чьи дети уже загружены (иначе лавина запросов).

## 5. Поведение и доступность

- Таблица получает `role='treegrid'`, строки данных `aria-level` (уровень + 1), `aria-expanded` только у узлов с детьми, `aria-setsize` и `aria-posinset` среди соседей (при виртуализации в DOM нет всех соседей, поэтому нужны явные значения). `aria-rowcount` и `aria-rowindex` как в гриде.
- Шеврон это `button` с `aria-expanded` и подписью из `levelLabels.expand(title)` и `levelLabels.collapse(title)`, где `title` это текст ячейки дерева. Лист вместо кнопки рисует пустой `span` той же ширины, чтобы названия выравнивались.
- Клик по строке не раскрывает узел (выбор строки работает как в гриде); раскрывает шеврон. Двойной клик по неинтерактивной части строки вызывает `onRowDoubleClick` как в гриде.
- Фокус при исчезновении строки из окна (сворачивание родителя) уходит на корень, как в гриде (`rescueFocus`).
- Живая область: после раскрытия или сворачивания не объявляем ничего (иначе шум); после загрузки страницы объявляется «Найдено N записей» как в гриде.
- RTL: отступ и шеврон работают через `padding-inline-start` и `inset-inline-start`.

## 6. Виртуализация и производительность

Цель владельца: 1000+ записей без лагов, как минимум десятки тысяч узлов.

- Окно рендера то же (`createVirtualWindow` на TanStack Virtual), строки ключуются индексом; в DOM только видимые плюс overscan 12.
- Раскрытие узла не пересоздаёт окно: меняется `itemCount` и содержимое индексов, строка с тем же индексом сохраняет DOM и меняет вид (как `GridItemRow`).
- Индекс «родитель → дети» и ключи строк не пересчитываются при раскрытии; плоский список строится за O(видимых).
- Пейджер необязателен: при `total` он включает нижнюю полосу и режет по страницам, как в гриде. В дереве страница считается по корневым узлам или по всем строкам `rows`: это решение страницы (она присылает `rows` и `total`), TreeList страницы не режет сам.
- Целевые цифры проверяются в playground на 20 000 узлов: раскрытие уровня и «развернуть все» на 5 000 узлов без заметной паузы (измеряется как время до следующего кадра, порог фиксируется в плане).

## 7. Макет

Макет TreeList (артефакт «TreeList — дизайн», артборды `Main`, `Dark`, `States`) нарисован классами макета грида, а не новым видом. Что он показывает и что должен повторять код:

- рамка, высоты (строка и шапка 32), шрифт 14, линии между строками и колонками, закреплённая первая колонка с правой границей `border-strong` без тени, меню колонки в шапке, стрелка сортировки слева от названия, выбранная строка заливкой;
- полоса сверху: пусто слева, справа четыре кнопки уровней;
- узел: отступ `level * 16`, шеврон 14 px в кнопке 20 px (`.gico`), лист с пустым местом под шеврон;
- состояния: догрузка детей («Загрузка…» и скелетоны), загрузка страницы (полоса прогресса и скелетоны с отступом по уровням), «Ничего не найдено», узлы: свёрнут, развёрнут, лист, фокус на шевроне, выбрана, наведение;
- футер: пейджер и «Обновить» справа внизу (тот же `GridFooter`).

Правило синхронизации макета и кода: скил `solid-kit-design-sync`. Опираться на макет при реализации, расхождение числа решается в пользу кода (токены), замысла в пользу макета. После реализации выполняется сверка и в итогах (раздел 12) фиксируется, что синхронизировано.

## 8. Стили

- Все стили узла (`.node`, `.node-expander`, отступ) добавляются в `grid.module.css` рядом со стилями группы: это общий CSS-модуль, нового нет. Нативная вложенность (`&`), токены `--s-kit-*`, тот же порядок правил.
- Новых токенов нет, кроме, возможно, `--s-kit-grid-expander-size` (20 px) если шеврон-кнопка в гриде и в дереве должна быть одного размера; тогда заводится один токен и используется в обоих местах.
- Строки TreeList получают `data-kind='row'` и `data-tree` (для стилей, зависящих только от дерева).

## 13. Риски и открытые места

- **Рефакторинг грида** самый рискованный шаг: `grid.tsx` 477 строк, тесты 1900+. Смягчение: шаг 1 отдельным коммитом без новых возможностей, перенос методом «вырезать и вставить» с неизменёнными тестами.
- **Ключи.** Группы грида это `string`, узлы дерева `RowKey` (`string | number`). Наборы раскрытых ключей двух режимов не смешиваются: в `GridBase` раскрытость приходит как функция и колбэк, а тип набора определяет оболочка.
- **Выбор без каскада.** Если BackOffice-экраны ждут «выбрал родителя, выбраны дети», добавим пропс после первого использования.
- **Пейджер в дереве.** Постраничность по корням или по всем строкам зависит от страниц BackOffice; пока оставляем решение страницам.
